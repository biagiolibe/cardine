## The six gaps

Quotes are from `docs/ADR_CARDINE_1_0.md:770–792`. Every test below uses the common disposable-clone harness: create a temporary directory and local bare remote, clone the candidate repository with its tags, configure a local Git identity, create a task branch and commit each fixture before invoking `python3 scripts/release.py prepare --version <next> --date 2030-01-01` without `--dry-run`. No test contacts GitHub or PyPI. For successful preparations assert the actual release commit and run `python3 scripts/check_repository.py` and `python3 -m unittest discover -s tests` in the clone; also assert the script's own validation ran unmocked. For expected preflight refusal, assert the tree and HEAD unchanged, then add the missing fixture and perform the successful real preparation and validation. Dispose of the entire temporary directory afterward.

1. > The release kind follows what changed. A template change without a migration stops the release; it is never labelled CLI-only.

   Today `require_migration_for_template_changes` at `scripts/release.py:173` checks templates against the last tag only on the CLI-only path (`derive_release:197`); keep this fail-closed comparison and extend its managed-surface inventory in `derive_release`. **R1** test: commit a template change without a migration, expect refusal, then add a valid migration and upgrade notes and prepare for real; assert template-changing kind in ledger and notes.

2. > One release can ship several migrations, and the version advances once, at preparation. The repository checks, the release script, and the contributor guide describe one procedure. In Meridian they described two, and a release could carry only one migration.

   `derive_release:193–207` already collects IDs with the same target, but `preflight:245–253`, `ensure_not_already_prepared:265`, `scripts/check_repository.py:646` and `CONTRIBUTING.md:458–463` embody the split procedure. Rewrite `preflight`, `derive_release`, `ensure_not_already_prepared` and `check_migrations` so several pending migrations can target the selected new release without an earlier version bump; reconcile `check_releases:704` and ledger reader. **R1** test: commit two valid pending migrations targeting the same next version, leave `VERSION` at the prior release, prepare once, assert both IDs, one version advance and all checks; rerun must not bump again.

3. > When Cardine manages its own repository, a template-changing release brings those project files to the new baseline in the prepared commit.

   `write_release:311–324` writes only release metadata and removes fragments; it does not upgrade the self-hosted project. Extend `prepare_main` to plan and apply the existing `src/cardine/templates/upgrade.py` `plan_upgrade`/`apply_upgrade` against the clone before validation and include exactly its managed outputs in the release commit. Preserve unmanaged text and refuse conflicts. **R2** test: install an older managed baseline in the disposable clone, commit a migration and template change, prepare for real; assert managed files and manifest match the new baseline, unrelated text survives, and both validation commands pass. Inject a conflict and assert no partial release, then fix it and prepare.

4. > Preparation runs on the task branch in the task worktree. Meridian's `release.py prepare` accepted only `main`, so the release task stopped with `RULE_CONFLICT` and fell back to the manual procedure. Publication stays a developer step on `main`.

   `preflight:239–241` requires `main`; `publish_preflight:634–637` separately requires `main`. Rewrite preparation preflight to verify a clean task worktree and branch, leaving the publication gate intact. **R1** test: clone, create a linked worktree on a task branch, prepare there for real and validate there; assert primary clone unchanged and publication preflight rejects the task branch.

5. > Tests never pin the framework's own `VERSION`. A test that needs a baseline asserts the baseline, so a CLI-only release does not fail the suite.

   The real unmocked suite in `validate:336–348` exposes pins; inspect all readers with `rg -n 'VERSION|frameworkVersion' tests`, distinguishing intentionally synthetic historical fixtures such as `tests/conversion_fixture.py:42`. Rewrite only assertions that read the checkout's current version to compare the relevant baseline, not arbitrary historical fixture values. **R3** test: real CLI-only preparation in the clone runs the full suite after the bump; a focused regression asserts a baseline remains unchanged across that bump.

6. > One maintainer document, `docs/RELEASING.md`, holds the release procedure, and the release task names it. `CONTRIBUTING.md` keeps only the rules for outside contributors and links to it.

   `CONTRIBUTING.md:395–496` contains both paths; `release.py:265–283` directs users to publication instead of a single prepare path. **R5** test: prepare in the clone for real using the new document's commands, run both validation commands, and check document links and release-task reference resolve. Assert contributors can find fragment and compatibility rules without a second maintainer procedure.

## PyPI

`pyproject.toml:1–17` uses Hatchling, project name `cardine`, a dynamic version from `VERSION`, Python >=3.12 and a `cardine` entry point; it has a development description and wheel package selection. R4 must make distribution metadata and included runtime/template assets suitable for installation, build both sdist and wheel with `python -m build`, inspect them and install each in an isolated environment to exercise `cardine --help`. The GitHub release workflow currently builds and uploads neither artifact. Add a gated build and PyPI upload job after validation, using `pypa/gh-action-pypi-publish`; test the workflow structure and build/install locally without uploading.

Credential choice remains DD2. For trusted publishing the developer configures a PyPI trusted publisher bound to this repository, workflow and protected environment; CI receives a short-lived OIDC identity with `id-token: write`. For a token the developer stores a project-scoped token in a protected GitHub environment secret; only the upload job consumes it. An agent neither handles credentials nor publishes. After the release commit lands on `main`, the developer runs `python3 scripts/release.py publish --confirm v<VERSION>` on `main`; the pushed tag triggers `.github/workflows/release.yml`, whose protected upload job publishes to PyPI and creates the GitHub release. The implementation must report partial success and safe inspection/recovery without moving a tag or blindly re-uploading immutable files.

## One procedure

`docs/RELEASING.md` will cover prerequisites and decisions; fragment and migration readiness; task-branch preparation and real validation; inspection and landing; developer-only publication on main; GitHub and PyPI verification; and interruption/partial-publication recovery. ## Developer decisions

- **DD1 — PyPI project name?** Keep `cardine`, or choose a distinct name and change package metadata and installation instructions. Read-only check on 2026-11-06: [PyPI's cardine page](https://pypi.org/project/cardine/) lists a 0.0.1 placeholder and `biagiolibe` as maintainer. The name is already registered, not available for a new registration; this public listing does not establish current account access. Recheck ownership before publication.
- **DD2 — Credentials?** Trusted publishing avoids a long-lived token but requires matching PyPI publisher configuration and GitHub OIDC/environment permissions. A project-scoped token works without OIDC but requires secret storage, rotation and revocation. The developer configures either; the plan chooses neither.
- **DD3 — First version published by this procedure?** Publish a 0.9 field-trial release before 1.0.0 as ADR work item 13 describes, or decide another first usable version and reconcile the ADR before implementation. The existing 0.0.1 placeholder already occupies that version; PyPI files cannot be overwritten. Version choice controls metadata, tags and release notes.
