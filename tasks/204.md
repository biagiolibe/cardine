## Objective

On 2026-11-08 task 201 committed a new implementation after a contract revision, and
every `cardine run 201` answered `ACCEPTANCE_UNMET: A complete committed implementation
must be delivered first`. The cause is in `run_validation_step` in
`src/cardine/lifecycle/engine.py`:

```python
pending = operation_path(root, task_id).exists()
if not pending and implementation_delivery(locations) is None and _committed_implementation(locations, state):
    delivered = deliver_run_implementation(locations)
```

`operation_path` is the validation intent `.git/cardine-operations/<ID>.validation`.
It stays on disk after an attempt ends, with phase `complete` or `invalidated`, so
after the first validation attempt the engine never delivers again. This blocks every
repair after a failed task or candidate validation, not only after a contract revision.
The implementer commits the fix, `cardine run` skips the delivery, and validation refuses
the stale one. Task 201 got past it with the explicit `cardine execution deliver`.

This task treats the validation intent as pending only while its phase is neither
`complete` nor `invalidated`:

```python
path = operation_path(root, task_id)
pending = path.exists() and receipts._load_intent(path).get('phase') not in ('complete', 'invalidated')
```

An attempt in progress (`process` or `publish`) still blocks a new delivery, as it does
today.

No prototype was made: the cause is the line above.
