## Objective

The console loads the task list slowly. On 2026-11-08 the coordinator measured
`load_snapshot` on this repository with the installed runtime and the console's own
caches (`IdentityCache`, `DeliveryCache` reused across calls):

- about 6 s for the first load, which the console shows as an empty screen, and about
  5.5 s for every later refresh;
- 115 `git` subprocesses per warm refresh, about 40 ms each on this machine (a bare
  `git rev-parse HEAD` takes 34 ms here);
- about 2 s of each refresh in `_orphaned_cleanup_task`. For each of the 11 landed tasks
  whose cleanup intent `.git/cardine-operations/<ID>.cleanup.json` is kept as the landing
  record, it replays `preview_run` (and so `_landed` and its Git checks) on every refresh.
  This cost grows by one task every time a task lands;
- 24 `rev-parse --verify --quiet refs/heads/<branch>` calls, one per task, from
  `_branch_observation`, and 15 `log -1 --format=%ct <ref> -- <record>` calls, one per
  record, from `_committed_update`.

The console asks for a refresh every 2 s, measured from the start of the previous one
(`last_poll` in `run_terminal`, `src/cardine/console/entry.py`). A refresh that takes
5.5 s is therefore followed immediately by the next one, and the console spawns Git
without pause.

After this task, a warm refresh no longer depends on the number of landed tasks, reads
the task branches with one Git command, and the next refresh starts 2 s after the
previous one ended. The engine's checks do not change: the console stays read-only and
only caches what it displays.

## Acceptance Criteria

- [ ] **Landed tasks.** The console keeps, across refreshes, the `done` result of
  `_orphaned_cleanup_task` for a task, keyed on the size and modification time of its
  cleanup intent, the commit of `refs/heads/main`, and the existence and modification
  time of the task's worktree path (no Git command). While the key is unchanged, the
  task is not previewed again. A result other than `done` is never cached. A test in
  `tests/test_console_snapshot.py` checks, by counting `preview_run` calls, that a
  second refresh with three landed tasks previews none of them, and that changing the
  intent, moving `main` or creating a file in the worktree path previews that task again.
- [ ] **Branches.** One `git for-each-ref` per refresh gives the commit of every
  `refs/heads/*` branch, and `_branch_observation` uses it instead of one
  `rev-parse --verify` per task. A test checks that the number of Git commands for this
  part does not grow with the number of tasks.
- [ ] **Record dates.** `_committed_update` results are kept across refreshes, keyed on
  the record path and the commit the ref resolves to, so an unchanged `HEAD` or branch
  asks Git again for nothing. A test checks it.
- [ ] **Refresh interval.** The next background refresh starts `interval` seconds after
  the previous one finished, not after it started. A test in
  `tests/test_console_refresh.py` checks it with a slow fake load.
- [ ] The displayed snapshot is unchanged: the existing console tests pass, and
  `tests/test_command_context.py` still passes its snapshot budget without being edited.
- [ ] **Measurement.** The handoff reports, for this repository, the time and the number
  of Git subprocesses of three warm refreshes before and after the change. Method:
  in-process Python from the task worktree, `load_snapshot(<primary checkout>,
  IdentityCache(), DeliveryCache())` called three times with the same cache objects,
  wrapping `subprocess.run` to count calls; "before" imports `src/` of `main`, "after"
  imports the worktree's `src/`. It is read-only and never a stop.
- [ ] Only the files under Expected code surface are edited, together with this task's
  own record, handoff, and state.
- [ ] Every source and test file stays below 1,500 lines.
- [ ] **Task validation.** After the implementation commit, `cardine run` measures the
  commands under Validation; record the `task-tests` result line in the handoff.
- [ ] Every command under Validation passes.

## Technical Context

- A landed task shown as `done` from the cache, while the developer has just reused its
  worktree path, is corrected by the worktree-path part of the key; the engine itself
  keeps refusing a reused path whatever the console shows.
- `load_snapshot(project, identities, deliveries)` is also called by other code and by
  tests without caches. New caches may be added as an optional argument or as fields of
  an existing cache object; a call without them behaves as today.
- Task 199 changes `observe_run` in `src/cardine/lifecycle/preview.py` for completed
  cleanups. This task does not edit `preview.py` or `cleanup.py`, and its cache sits
  around the console's call, so the two tasks land in either order.
- The project's standing decisions are in `PROJECT_WORKFLOW.md`, section `Standing
  decisions`.
