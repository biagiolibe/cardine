## Objective

After `cardine setup --apply`, every new Claude Code session in the project opens
with 24 warnings:

```text
⚠ Deny rule MultiEdit(/.cardine/tasks/**) matches no tool · check for typos
⚠ Deny rule Write(/.cardine/tasks/**) never matches · use Edit(/.cardine/tasks/**)
⚠ Deny rule NotebookEdit(/.cardine/tasks/**) never matches · use Edit(/.cardine/tasks/**)
```

`CLAUDE_PROJECT_DENYLIST` in `src/cardine/hosts/claude.py` writes one rule per name
in `permissions.NATIVE_WRITE_TOOLS` (`Edit`, `Write`, `MultiEdit`, `NotebookEdit`)
for each protected path. Claude Code applies an `Edit(...)` rule to every built-in
tool that edits files, has no `MultiEdit` tool, and reports the other rules as never
matching. The `Edit(...)` rules are present, so the protection holds; the other 18
rules are noise that every Cardine user sees.

Write only `Edit(...)` rules in Claude settings, in the project deny list and in the
role policy, and let setup remove the exact obsolete rules that earlier versions
wrote, so that an installed project stops warning after one `setup --apply`.
`permissions.NATIVE_WRITE_TOOLS` stays unchanged: the hook evaluator still judges
each tool name a host may send.

## Technical Context

- Claude Code documents that `Edit(...)` permission rules apply to all built-in tools
  that edit files. The session warnings above confirm it on this machine
  (Claude Code 2.1.319).
- Removing an obsolete rule never widens access, because the `Edit(...)` rule for the
  same path stays. That is why setup may remove these exact strings, unlike
  `LEGACY_ALLOW_ENTRIES`, whose removal would change what is allowed.
- `tests/fixtures/module_split_baseline.json` names `CLAUDE_PROJECT_DENYLIST`; the
  name is unchanged.
- During development, run only what the change touches: `python3
  scripts/run_tests.py --parallel --module <name>`, repeating `--module`. Do not run
  `python3 -m unittest` directly. Run the full suite once, as the counted
  clean-clone validation.
- Run validation suites one at a time and redirect each one's output to a log file
  with its exit code appended, so the result survives a lost process handle.
- Other tasks share this machine. Stop only your own processes, by process ID;
  never `pkill` test runs by pattern.
