## Objective

`cardine setup --apply` writes `.claude/settings.local.json`, the command allowlist and
deny rules of one machine, but nothing tells Git to ignore it. A developer whose
global Git excludes lack the rule that Claude Code adds when it creates the file
itself meets one of two failures:
- an ordinary `git add -A` commits the file;
- left untracked, it makes the primary checkout dirty, and landing stops:

```text
BLOCKED PRIMARY_DIRTY: primary checkout must be clean
```

The coordinator met both on 2026-11-08 while rehearsing the README's first task in a
disposable project with a disposable `HOME`. With this task, `setup` plans one entry,
`/.claude/settings.local.json`, in the repository's own `info/exclude`, shows it under
`--check`, and writes it under `--apply` in the same journaled operation. That file
is never committed, so the project's `.gitignore` stays untouched. Setup changes
nothing when Git already ignores or tracks the file, or outside a repository.

## Technical Context

- Task 190 edits `src/cardine/hosts/claude.py`, which writes the settings file. This
  task stays in `src/cardine/hosts/setup.py` so that the two tasks share no line and
  can land in either order.
- Task 194 ignores the machine-local files under `.cardine/` through a generated
  `.cardine/.gitignore`. That file cannot reach `.claude/`, and adoption keeps the
  project's own `.gitignore`, hence `info/exclude`.
- `git rev-parse --git-path info/exclude` names the common directory's file, so a
  linked worktree shares the entry.
- `setup --apply` on a project that has not been initialized also writes
  `.cardine/project.json` and `.cardine/candidate-validation.json`; that is a separate
  defect, out of scope, and the new test asserts only on `.claude`.
