# Task 251 — Make init interactive and publish the configuration

> **ID**: `251`
> **Category**: Feature
> **Priority**: 🟠 P2
> **Estimate**: ~3h
> **Assigned to**: unassigned
> **Session**: Onboarding, 2026-11-11
> **Origin**: P3 and P4 of the onboarding design

## Objective

1. With no mode flag, `cardine init` defaults to the current project and uses
   `_interactive()` from `src/cardine/lifecycle/control.py` to require a TTY on
   stdin and stdout. Otherwise emit a usage error naming `--check` and `--apply`.
2. Plan before writing. Select adoption when the adoption plan detects an existing
   installation or conflicting paths. Show each choice and its source using the
   defaults from task 248. Prompt once per choice and keep the displayed value on
   Enter. Ask for a test command when validation cannot be inferred. Show the final
   plan and apply it after confirmation. For adoption, use
   `apply_rehearsed_adoption`, which handles the disposable rehearsal.
3. Show the repository paths written and the proposed commit message. Ask a second
   confirmation before committing only those paths and pushing `main`. Preserve
   unrelated staged and unstaged changes. Refuse to include pre-existing edits
   to paths in the plan. If a push fails, preserve the commit and print the cause
   and exact retry command. Use explicit paths and ordinary pushes.
4. Document interactive init in `docs/PUBLIC_SURFACE.md`. In `cardine-project`,
   require an explicit mode flag on every agent call to init or adopt, including
   on hosts that allocate a pseudo-terminal.

## Acceptance Criteria

- [ ] Patched stdin and stdout exercise TTY init, adoption routing, default and
  edited choices, both confirmations, and refusal without a TTY.
- [ ] Declining apply leaves project files untouched. Declining publication
  leaves applied files available to the developer. Accepting both confirmations
  creates a commit with only the paths written and pushes to a local bare remote.
- [ ] Unrelated staged and unstaged paths stay outside the commit. A rejected
  push leaves the local commit and prints the cause and retry command. The flow
  never uses force push or `git add -A`.
- [ ] Explicit `--check` and `--apply` retain existing output and behavior and
  never prompt, even with a TTY. Existing adopt modes retain their behavior.
- [ ] The repository checks and targeted validation pass.
