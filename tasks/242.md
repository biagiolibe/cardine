# Task 242 — Guide new Cardine projects to their first landing

> **ID**: `242`
> **Category**: Feature
> **Priority**: 🟠 P2
> **Estimate**: ~2h
> **Assigned to**: unassigned
> **Session**: Project onboarding, 2026-11-10
> **Origin**: friction

## Objective

Give maintainers and agents a single way to learn how to use Cardine from a
newly initialized or adopted checkout. Show the path to a first integrated
task, what the project can already use, and what the maintainer needs to
configure or decide next.

## Acceptance Criteria

- [ ] Successful `init --apply` and `adopt --apply` point to
  `cardine guide --project <checkout>`. Preview and rehearsal retain their
  existing meaning and output contracts.
- [ ] The guide runs from an initialized or adopted checkout and has readable
  text and structured JSON output from the same facts. It is read-only and
  works offline. It reports unknown or unverified facts explicitly and never
  claims a host policy or remote CI check is effective from local settings alone.
- [ ] The first-task path explains checkout and remote prerequisites, host
  setup and doctor, task registration and publishing its record, and following
  `cardine run` to verified landing, including when independent review or CI
  is required. An isolated walkthrough starts from a freshly initialized or
  adopted project and reaches a first landing using the documented steps.
- [ ] The guide distinguishes project defaults, per-task choices, and missing
  prerequisites for local validation, review, Authority and expected code
  surface, spikes and dependencies, CI before landing, host setup and doctor,
  and the console. Recommendations reflect the resolved project declaration.
  Cover a lean project without CI and a project with CI configured. Explain
  that the maintainer supplies the CI workflow and that required checks must
  report on the task branch commit.
- [ ] An agent can discover the same guide through the Cardine project skill
  and the installed project router when asked how to use Cardine. The agent
  uses project facts to suggest relevant next steps and leaves decisions and
  configuration changes to the maintainer.
- [ ] Tests cover both setup entry points, text and JSON, representative
  configurations, and the guide's read-only behavior. Document the entry
  point in the Quickstart and public CLI surface.

## Technical Context

The Quickstart already describes the manual path. The installed routers map
known commands to procedures, but new users and agents still need a starting
point that connects those procedures to the active project. Reuse the resolved
project model and link to canonical documentation for deeper coverage.
The guide explains available options without enabling them.

## Out of scope

Automatic setup, authorization, CI provisioning, policy changes, release or
migration work, and console performance or layout changes.
