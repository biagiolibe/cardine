## Question

Which refusals on the path of a task (preparation, delivery, validation, candidate,
finalize, cleanup) does the engine resolve by itself, and which need the developer?
Today the classification is accidental:

- `dispatch` in `src/cardine/lifecycle/engine.py` turns every untyped `CardineError` into
  `COMMAND_REFUSED`, which `capabilities/stop-codes-v1.json` marks
  `human_decision: true`. Hundreds of internal checks therefore ask the developer for a
  decision, even when the engine knows the only safe next step.
- Several operations refuse when an interrupted operation meets changed inputs: for
  example `delivery input source changed`, `preparation input or owner changed`,
  `host preview has foreign owner or changed inputs`, `finalize task inputs changed`,
  `closure commit inputs or owner changed`. Task 201 resolves this for task and candidate
  validation only. There it was safe because an interrupted attempt has published no
  result.

## Timebox

3 hours. If the inventory is not complete within it, deliver the classification rule and
the inventory of the modules finished, and list the rest.

## Deliverable

`docs/ENGINE_STOP_CLASSIFICATION.md`, containing:

1. **The rule.** Every refusal on the path of a task falls into one class:
   - *tamper or integrity*, such as a forged receipt or a foreign owner: stays a developer
     stop;
   - *interrupted without effect*: the engine restarts the operation;
   - *interrupted after an effect*: the engine finishes or reverses that effect, or stops
     with the exact state;
   - *live concurrent operation*: the engine waits with `retry_after_seconds`;
   - *precondition the engine can satisfy*, such as committing its own records.
2. **The inventory.** Each `raise CardineError` or `raise stop_error` in the modules
   above, with file and line, its class, and the reason. A refusal whose class depends on
   whether an effect already happened names the boundary that decides it.
3. **The proposal.** How `dispatch` learns the class: typed exceptions, or one code per
   class in the stop registry, with the smallest change that keeps tamper refusals as
   developer stops.
4. **The follow-up tasks.** Each one is small enough for one implementer session, with the
   files it would touch.

## Objective

Give the coordinator a written decision from which to plan the fixes, instead of finding
each refusal when a task stops on it.
