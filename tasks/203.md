## Question

Which refusals on the path of a task (preparation, delivery, validation, candidate,
finalize, cleanup) does the engine resolve by itself, and which need the developer?
Today the classification is accidental:

- `dispatch` in `src/cardine/lifecycle/engine.py` turns every untyped `CardineError` into
  `COMMAND_REFUSED`, which `capabilities/stop-codes-v1.json` marks
  `human_decision: true`. Hundreds of internal checks therefore ask the developer for a
  decision, even when the engine knows the only safe next step.
- Several operations refuse when an interrupted operation meets changed inputs: for
  example `delivery input source changed`, `preparation input or owner changed`,
  `host preview has foreign owner or changed inputs`, `finalize task inputs changed`,
  `closure commit inputs or owner changed`. Task 201 resolves this for task and candidate
  validation only. There it was safe because an interrupted attempt has published no
  result.
- A stop rarely says what changed or what to do. On 2026-11-08 task 198 stopped with
  `foreign candidate ownership or changed task source`. The actual cause was that the
  task branch had moved past the commit staged for the candidate, and the fix was to
  move it back. The coordinator had to read the engine source to find this.

A second question: how do project-wide decisions reach the agent? Every task record
repeats about 40 lines of "Developer decisions given in advance" and development
guidance: how to run tests, retry limits, process hygiene. The records carry them so
that they hold however the task is launched (ADR decision 12). Each implementer reads
all of them up front, whether or not the situation arises. Part of that text
compensates for stops classified as above and should disappear with them. The rest is
project policy and needs a mechanism.

## Timebox

5 hours. If the inventory is not complete within it, deliver the classification rule and
the inventory of the modules finished, and list the rest.

## Deliverable

`docs/ENGINE_STOP_CLASSIFICATION.md`, containing:

1. **The rule.** Every refusal on the path of a task falls into one class:
   - *tamper or integrity*, such as a forged receipt or a foreign owner: stays a developer
     stop;
   - *interrupted without effect*: the engine restarts the operation;
   - *interrupted after an effect*: the engine finishes or reverses that effect, or stops
     with the exact state;
   - *live concurrent operation*: the engine waits with `retry_after_seconds`;
   - *precondition the engine can satisfy*, such as committing its own records.
2. **The inventory.** Each `raise CardineError` or `raise stop_error` in the modules
   above, with file and line, its class, and the reason. A refusal whose class depends on
   whether an effect already happened names the boundary that decides it.
3. **The proposal.** How `dispatch` learns the class: typed exceptions, or one code per
   class in the stop registry, with the smallest change that keeps tamper refusals as
   developer stops.
4. **Stop messages.** What every remaining stop must carry: what changed (expected and
   found values), why it matters, and the exact command or action that resolves it. Apply
   this to the stops in the inventory that stay developer stops.
5. **Project decisions.** A mechanism for project-wide standing decisions that meets
   three constraints:
   - *Frozen*: the contract records the digest of the decisions in force at task creation,
     as it already does for the validation policy and the execution evidence profile. A
     later change reaches a task only through `cardine task contract update`.
   - *Delivered at the step*: the `cardine run` output carries the decision that applies
     to the step it reports, so an implementer who never meets a validation failure never
     reads the rules about failures. The full effective contract (record plus frozen
     decisions) stays readable in one place, for example through
     `cardine execution contract`.
   - *Enforced before written*: a decision the engine can enforce, such as limits, scope
     or commands, becomes a check, not text. Only rules that need judgment stay as text,
     and the session briefing (`cardine hook briefing`) delivers them.

   The section also classifies the current "Developer decisions given in advance" block
   line by line: *removed by the stop fixes*, *enforced by the engine*, *project
   decision*, or *task-specific*.
6. **The follow-up tasks.** Each one is small enough for one implementer session, with the
   files it would touch.

## Objective

each refusal when a task stops on it.
