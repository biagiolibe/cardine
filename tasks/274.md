# Task 274 — Stop when the CI provider never starts a run for the delivered commit

> **ID**: `274`
> **Category**: Fix
> **Priority**: 🟠 P2
> **Estimate**: ~2h
> **Assigned to**: unassigned
> **Session**: CI wait without a run, 2026-11-11
> **Origin**: friction

## Objective

On 2026-11-11, tasks 267 and 268 of this repository delivered `c7a8992` and `b113e87`,
and `cardine run` pushed them to their task branches. GitHub created the two workflow
runs but never their jobs, so both runs stayed `queued` and neither commit has any check
run. Every `cardine run 267 --ci-wait-seconds 900` waited out its budget and returned
`outcome: waiting`, `action: poll-ci`, with the diagnostic `CI_PENDING`, "CI wait budget
of 900 seconds expired for <sha>; pending checks: validate". Nothing said that no run
existed. An agent following `next` would loop forever, because the engine never pushes
again once the push is recorded.

### 1. Name the missing run

In `query_checks` and `ci_gate` (`src/cardine/integration/ci.py`), tell apart two cases:

- **pending**: at least one required check run exists for the head and is not completed.
  Behaviour and diagnostic stay as today.
- **not started**: no check run whose `head_sha` is the head and whose `name` is a
  required check.

When the outcome is `waiting` and the run has not started, the diagnostic is
`CI_NOT_STARTED`, with the message "no `<checks>` check run exists for <head> on
<repository>; the provider has not started CI for this commit".

### 2. Stop instead of waiting forever

When `--ci-wait-seconds` is at least 300, the budget expires, and the run has still not
started, `cardine run` stops with a new stop code, `CI_NOT_STARTED`, instead of
returning `waiting`.

- `outcome` is `blocked` and `human_decision` is true.
- The detail names the head, the ref and the required checks. It says that pushing the
  same commit to another branch that triggers the workflow, for example
  `git push origin <head>:refs/heads/<ref>-ci`, starts a run that the gate accepts,
  because it matches check runs by `head_sha`.
- The resume command is `cardine run <ID> --project <primary> --ci-wait-seconds <same value>`.

Below 300 seconds, or without `--ci-wait-seconds`, the outcome stays `waiting` with the
diagnostic of part 1. A run may simply not have started yet.

Add the code to `capabilities/stop-codes-v1.json`, following the entries already there:
- class `tool`, step `C6`, kind `stop`, resolution `recoverable`;
- `human_decision` true;
- `emitter` `cardine.integration.ci.ci_gate`;
- `test` names the new test.

Register its cause where `src/cardine/stops/causes.py` registers the other run stops.

### 3. Document it

In `docs/RUN_COMMANDS.md`, in the paragraph on required CI, add one sentence: an
expired wait with no check run for the delivered commit stops with `CI_NOT_STARTED`,
and pushing the same commit to another branch that triggers the workflow resumes it.

## Technical Context

- **Developer decision** (2026-11-11): the engine must not wait forever on a commit
  that has no CI run.
- `query_checks` already ignores a run on another SHA and keeps the latest run per name
  (`ci.py` near lines 184 to 189). A run triggered by another branch for the same commit
  therefore counts. Keep that.
- 300 seconds is the threshold because, after a push, GitHub normally creates the check
  run within seconds to a minute. A shorter wait proves nothing.
- `validate.yml` has no `workflow_dispatch`, so the stop cannot name a dispatch command.
- Sweep every site that lists the stop codes before you finish:
  `git grep -n "CI_PENDING\|PUSH_REJECTED" -- src tests docs capabilities`.
- During development, run tests with
  `python3 scripts/run_tests.py --parallel --module <name>`.

## Out of scope

- Triggering CI from Cardine, or cancelling provider runs.
- Providers other than GitHub.
- The `CI_PENDING` behaviour when a run exists.
