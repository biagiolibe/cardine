## Objective

ADR decision 9 says that Cardine installs with `pipx install git+https://github.com/biagiolibe/cardine@v<version>`
or from PyPI, with templates and skills shipped as package data. Today only an editable
install from a clone works: the wheel holds the `cardine` package alone, and the runtime
reads its assets from the repository root, found as `Path(__file__).resolve().parents[3]`
or `SCRIPTS_ROOT.parent`. In a wheel that path is the interpreter's `lib/python3.12`
directory. This task makes a wheel install work and keeps the editable install working.
It is proposal P1 of `docs/ONBOARDING_DESIGN.md`.

### 1. Package the assets

In `pyproject.toml`, include these repository paths in the wheel under
`cardine/_framework/`, at the same relative paths (for example with hatch
`force-include`):

- `VERSION`
- `capabilities/`
- `schemas/`
- `migrations/`
- `templates/single/`
- `skills/`

Do not move any directory. `skills/`, `commands/` and `hooks/` at the repository root are
also the Claude Code plugin tree, and repository checks read them in place.

### 2. One framework-root resolver

Add `framework_root()` to `src/cardine/shared/paths.py`. It returns the first of these
that exists:

1. `CARDINE_ROOT`, when set (the existing development override).
2. The package data directory `cardine/_framework`, when it holds `VERSION`.
3. The repository root of a source checkout: the directory that holds `src/cardine` and
   `VERSION`.

Every reader listed under Relevant Files uses it instead of `parents[3]` or
`SCRIPTS_ROOT.parent`. Keep the name `SCRIPTS_ROOT` defined exactly once: the module
inventory baseline requires it. The CLI's `--framework-root` default becomes
`framework_root()`.

### 3. Runtime identity measures what runs

`_runtime_identity` in `src/cardine/lifecycle/receipts.py` hashes the executing runtime.
In a wheel its globs match nothing, so every version would get the same digest and
authorization would stop detecting a runtime change. Make it hash:
- the `cardine` package's own `.py` files, wherever it is installed;
- the framework data under `framework_root()`, from `capabilities`, `schemas`,
  `migrations` and `templates`.

The runtime location it binds is the package directory, not `parents[3]`. In a source
checkout the set of measured files must stay the same as today.

### 4. Launchers that do not need `bin/cardine`

- Add `src/cardine/__main__.py` so that `python -m cardine` runs `cardine.cli.main`.
- `launcher()` in `src/cardine/hosts/hooks.py` keeps `(sys.executable, <checkout>/bin/cardine)`
  in a source checkout. Elsewhere it returns `(sys.executable, "-m", "cardine")`, never a
  bare `cardine`: hosts started from a desktop app have no shell `PATH`. `owns()` must
  keep recognising both forms.
- `src/cardine/adopt/verify.py` runs the CLI as `sys.executable -m cardine`, not
  `framework/bin/cardine`.
- `src/cardine/adopt/rehearsal.py` sets `PYTHONPATH` to the directory that contains the
  imported `cardine` package, not `framework/src`.

### 5. Console without `scripts/`

`cardine console` checks for `scripts/project_console.py` before it starts. Make it
depend only on `cardine.console.entry`, which it already imports.

### 6. Prove the installed package

Add `scripts/check_installed_package.py`. It:
1. builds the wheel into a temporary directory with `python3 -m pip wheel --no-deps`;
2. installs it into a new virtual environment;
3. sets `HOME` to a temporary directory;
4. runs, with that environment's Python and none of the source tree on `sys.path`:
   - `cardine --version`, which must match `VERSION`;
   - `python -m cardine --version`;
   - in a new Git repository with one commit, `cardine init --project . --check` with
     complete arguments and a validation file whose test command is `true`;
   - `cardine adopt --project . --rehearse` on a copy of that repository;
5. asserts that the runtime digest covers at least one file and changes when one installed
   package file changes.

It exits non-zero on the first failure and prints which step failed. Add it to
`.github/workflows/validate.yml` as a step after `python3 scripts/check_repository.py`.

## Technical Context

- By developer decision, no prototype was made. The inventory of readers above comes
  from a search of `src/cardine` for `parents[3]`, `SCRIPTS_ROOT` and `framework_root /`
  on `main` at `cb35b71`.
- The surface is larger than ten files because the change is mechanical and cannot be
  split: a partial change leaves a runtime that works only in one layout.
- `setup` prints shell-profile lines that export `CARDINE_ROOT` and add
  `$CARDINE_ROOT/bin` to `PATH`. ADR decision 9 removes them, but that is out of scope
  here: leave them as they are.
- Building the wheel needs `hatchling`, which pip fetches from the network. That is why
  the package proof is a script run in CI, not a module of the unit suite. The unit suite
  stays offline.
- Standing scope clause: if another reader of repository-root assets turns up, convert
  it the same way and add it to the handoff. That is not a scope change. A reader outside
  `src/cardine` is a scope change.
