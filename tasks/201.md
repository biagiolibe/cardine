## Objective

Task 198 was implemented and validated by 03:16 on 2026-11-08, then spent the day
re-running its full validation. It could not close from Codex at all. The evidence ledger
holds four passing complete attempts and two failed ones on the same source digest. Only
the `environmentDigest` changed between them. Three defects combine:

1. **The environment makes every result stale.** `environment_identity` in
   `src/cardine/tasks/validation.py` digests all of `os.environ` except four keys.
   Codex sets `CODEX_TOOL_CALL_ID`, which differs on every tool call. Terminals set
   session keys. `verified_validation` therefore discards a passed attempt on the next
   `cardine run`, and the engine prepares a candidate only when it reuses a passed
   attempt unchanged (`before_validation == progress` in `run_validation_step`). The
   candidate binding in `src/cardine/integration/candidate.py` embeds the same digest,
   so a passed candidate would be re-run before finalization in the same way.
2. **The engine's own records fail its next attempt.** A passed attempt publishes the
   task state, the evidence ledger and the handoff into the task worktree without
   committing them. The next attempt runs `python3 scripts/run_tests.py --parallel
   --clean-clone`, which refuses a dirty tree with exit 2, and the refusal is counted as
   a validation failure.
3. **An interrupted attempt becomes a developer stop.** When an attempt that produced no
   result is interrupted, the next `cardine run` with different inputs refuses with
   `validation inputs changed during interrupted attempt`, which the engine reports as
   `COMMAND_REFUSED` with `human_decision: true`. The developer had to move
   `.git/cardine-operations/198.validation` aside by hand.

This task:

1. makes `environment_identity(environment, commands)` digest the program that each
   validation command's bare name resolves to on the environment's `PATH` (real path, or
   `None`). A name with a path separator, such as `scripts/check_repository.py`, is a
   file of the checkout, which the source digest already covers. Only a change that runs
   a different program makes a result stale;
2. adds `commit_own_records` in `src/cardine/lifecycle/validation.py`. Before a fresh
   attempt it commits the task's own uncommitted records (state, evidence, handoff,
   record, review) as `Record <ID> task state`, and only when nothing else is dirty.
   Foreign changes are left for the validation commands to judge;
3. replaces an interrupted task or candidate attempt whose inputs changed with a fresh
   attempt, instead of refusing. Such an attempt never published a result, and the
   runner lock excludes a live concurrent runner.

## Technical Context

- Validation commands run through `/bin/bash -c` with the caller's environment
  (`execute_command`), so the program a command name resolves to on that `PATH` is what
  the environment contributes to a result.
- Resolving a name that contains a path separator would depend on the current directory:
  the engine validates in the task worktree and later checks from the primary checkout,
  so the first prototype made ten tests in `tests/test_worktree_lifecycle.py` stale.
- `commit_own_records` commits through `git_output`, the product's single Git gateway
  that `test_command_context` enforces.
- `execution_source_digest` already excludes the task's owned paths, so committing them
  changes neither the source digest nor the validation inputs.
- `test_run_validation.RunValidationTest.shadowed_path` builds a `PATH` on which a
  command name resolves to a different program, the one environment change that still
  invalidates.
- After this lands, results measured with the old identity become stale once; each
  in-progress task re-runs its validation one time.
- The broader audit of engine stops (untyped errors reported as developer decisions,
  other interrupted operations, primary-checkout cleanliness) is out of this task.
- During development, run only what the change touches: `python3
  scripts/run_tests.py --parallel --module <name>`, repeating `--module`. Do not run
  `python3 -m unittest` directly. Run the full suite once, as the counted
  clean-clone validation.
- Run validation suites one at a time and redirect each one's output to a log file
  with its exit code appended, so the result survives a lost process handle.
- Other tasks share this machine. Stop only your own processes, by process ID;
  never `pkill` test runs by pattern.

## Developer decisions given in advance

The developer records these decisions in the task contract, so that they
hold however the task is launched, including a bare `Proceed with <TASK-ID>`
from the project console (ADR decision 12). None of these situations needs a
new decision from the developer. After fixing a failure, continue with
revalidation in the same turn; do not stop to report the fix.

- A required command that exits non-zero because of a precondition the agent
  can satisfy (command order, an uncommitted worktree, a missing argument):
  satisfy it and run the command again, once.
- A validation failure caused by this task's own changes: fix it and revalidate, at
  most 3 counted attempts. A test that fails once and passes on an identical
  unchanged rerun is intermittent, recorded in the handoff, and does not count.
  Only after 3 counted failures stop and summarize the failures.
- A counted attempt is one run of the whole Validation section on a committed
  implementation that the agent considers complete. Test runs during
  implementation are development, not attempts.
- Before the first clean-clone, run `python3 scripts/check_repository.py` and one
  `python3 scripts/run_tests.py --parallel` with one `--module` flag for each edited
  test module and for the repository guards: `test_module_inventory`, `test_layout`,
  the identifier guard (the `tests/test_no_*_identifiers.py` module),
  `test_text_gates`, `test_stop_registry`, and `test_command_word`. Repeat
  `--module`; a comma-separated list is refused.
- Let a started clean-clone finish; do not interrupt it. After a failed clean-clone,
  fix, commit, and run `python3 scripts/run_tests.py --parallel --last-failed` and a
  `--module` run for each module the fix touched before the next counted attempt.
- A stop printed by `cardine run` whose code in `capabilities/stop-codes-v1.json` has
  `human_decision: false`: run the command the stop names, once. If it stops again
  with the same code, stop.
- A test outside the listed files that fails only because it changed an arbitrary
  environment variable and expected a measured result to become stale, or expected an
  interrupted attempt with changed inputs to stop: change the environment the way
  `shadowed_path` in `tests/test_run_validation.py` does, or expect the fresh attempt,
  and list the file in the handoff. Any other change outside the listed files is a
  change of scope.
- Before stopping for a change of scope, finish everything else, commit it, and run
  the repository check and the affected tests, so that one stop names every file
  needed.
- A change of scope, a guardrail, and every action the project's workflow denies
  remain stops.
