# Task 249 — Show how to resume after a scope change

> **ID**: `249`
> **Category**: Fix

> **Estimate**: ~2h
> **Assigned to**: unassigned
> **Session**: Delivery workflow, 2026-11-11
> **Origin**: Task 246 scope-change recovery

## Objective

1. When `cardine run` finds changes outside the frozen Expected code surface,
   keep the single `SCOPE_CHANGE_REQUIRED` guardrail and the complete, sorted list
   of paths. Explain what the developer is being asked to approve. If the
   developer approves, tell the implementer to add only the approved paths to
   the task record in the task worktree, update Validation if the approved change
   requires another check, and run `cardine task contract update` for that worktree.
   Print the exact task ID, record path, worktree-specific update command, and
   primary-checkout `cardine run` command. Use the existing JSON diagnostics and
   the existing human-readable stop output.
2. When an implementer identifies necessary paths outside the frozen surface before
   editing them, request one approval naming the exact paths, why they are needed,
   and any validation change. Once approved, revise the record in the task
   worktree, update its frozen contract, edit the approved files, and resume
   `cardine run` from the primary checkout in the same session.
3. Document the two ways to clear the stop. An approved expansion is recorded in
   the frozen contract before validation resumes. If the expansion is declined,
   restore the change to the approved surface before rerunning the task.
   Document that the initial approval can include the precise record revision
   so the implementer can proceed in the same session.

## Acceptance Criteria

- [ ] For several changed paths outside the surface, one run reports all paths
  and the exact commands above. The result remains blocked with exit status 2
  and `human_decision: true`. The existing `stop.resume` and `next.command`
  still identify the primary-checkout retry. The contract update command
  addresses the task worktree and is quoted correctly for shell-sensitive paths.
- [ ] A disposable delivery fixture proves that retrying before the contract
  revision keeps the stop, then updates the record and uses the printed
  contract-update command. The frozen contract and its revision history reflect
  the approved paths, and the printed retry can continue through normal
  validation and landing. Exercise the alternative of removing the out-of-scope
  changes using the existing recovery coverage.
- [ ] An unsafe path or an absent or invalid expected surface retains its
  existing guardrail and receives no proposal to authorize unsafe paths.
  Printing guidance makes no change to the record, state, evidence, or refs.
- [ ] A preventive scope expansion is approved and frozen before the new files
  are modified, and the task can resume. The delivery skill and run documentation
  describe the single approval and same-session recovery.
- [ ] The affected validation modules and repository checks pass. The lifecycle
  records validation using the ordinary task evidence flow.
