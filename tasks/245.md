# Task 245 — Make released onboarding easy to follow

> **ID**: `245`
> **Category**: Fix
> **Priority**: 🟠 P2
> **Estimate**: ~2h
> **Assigned to**: unassigned
> **Session**: Release onboarding, 2026-11-10
> **Origin**: friction

## Objective

Make the README an easy entry point and the Quickstart a complete
walkthrough from a GitHub release page to a first integrated task. Keep
the install instructions and the commands in the walkthrough compatible
with the same published release.

## Acceptance Criteria

- [ ] The README presents two clearly labeled starting paths, terminal
  and agent, and links to the corresponding Quickstart sections. Keep
  the delegation line and the self-contained agent prompt identifying
  the official repository and the matching Quickstart. Keep one
  canonical walkthrough and remove the circular link and duplicated
  tutorial. Update affected anchors and references.
- [ ] Make the project console discoverable in the README near Get started.
  Explain that it lets maintainers inspect task status and see the next
  action from an interactive terminal. Link to a short Quickstart section
  showing how to open it from the project checkout with
  `cardine console --project .`, select a task, open its details, search,
  and quit. Verify the documented keys against the advertised tag. Describe
  newer behavior from task 244 only on a path that provides it, and keep
  the console optional in both onboarding paths.
- [ ] Near Get started in the README, embed a real screenshot captured
  from the console running against a disposable example project. Show a
  task in progress with the Elapsed and Gate columns visible and readable.
  Add alt text and a caption identifying the version shown. If the capture
  uses unreleased code, label it as a development preview and identify
  the commit used so readers can distinguish it from the published tag.
  Keep private project names, local paths, and credentials out of the image.
- [ ] The Quickstart separates installing the CLI from connecting an
  agent host. It explains what terminal-only users need, what Claude
  Code users install, and when Codex gets the project skills. It states
  who runs each step and where the maintainer reviews or consents.
- [ ] At the first occurrence of `--task-identity`, explain in the Quickstart
  that `opaque` allows simple IDs such as `001` and `002`, while
  `milestone` requires a milestone, workstream, and sequence, such as
  `M1-API-001` and `M1-API-002`. In the agent walkthrough, ask how the
  maintainer wants to number tasks using those examples in plain language,
  then map the confirmed choice to the CLI flag. Verify this question in
  the agent walkthrough evidence.
- [ ] Introduce Contoso explicitly as a fictional example before its
  first use and identify every value readers replace. Distinguish the
  Cardine runtime clone from the project checkout. Show explicit clone
  and directory-change commands for an existing project that is not
  yet local, an explicit directory change for an existing local
  checkout, and concrete commands to prepare a new Git repository,
  its main branch, and a writable origin.
- [ ] The canonical walkthrough shows complete init and adopt examples.
  Separate preview, rehearsal where applicable, and apply so the
  maintainer can inspect each result. Show the working directory,
  expected result, and relevant recovery action at each point. Include
  the complete first-task example and instructions to verify that it
  reached main. Stage intended files only or explicitly require a
  clean checkout and review of the staged changes before committing.
- [ ] End the Quickstart with a section on everyday use after the first
  landing. Explain that the maintainer describes a goal, supplies domain
  knowledge, reviews proposals, and makes required decisions. The agent
  inspects the project, drafts specifications, defines acceptance criteria,
  validation commands, code scope and dependencies, registers and publishes
  the task under the project's permissions, and drives the run loop.
  Include a version-checked table mapping goals to requests for the agent,
  actions the agent performs, and any action required from the maintainer.
  Cover status and console, task creation, execution and lifecycle
  orchestration, independent review and remediation, waits and stops,
  cancel versus abort, host diagnostics, and links for spikes, CI, and
  maintenance. Present CLI commands as agent actions or diagnostic
  references. Direct user commands are for installation, console access,
  and explicitly required maintainer approvals.
- [ ] After the first done result, the agent shows what landed, offers
  a prompt to describe the next real goal, and points to everyday-use
  guidance. Users who installed from the terminal receive the same
  agent-led operating model. Verify examples against the advertised
  release. The agent does not start another task without a chosen goal.
- [ ] Installation, plugin pinning, documentation links, and walkthrough
  commands agree with the advertised published tag. In particular, the
  v0.9.1 path must work without the guide command. Present guide only
  on a path that explicitly uses a version that provides it. Document
  how a later release switches the recommended path without leaving
  contradictory version references.
- [ ] Run two isolated walkthroughs starting on the actual GitHub page
  for the advertised published release, with no existing Cardine clone
  or project configuration. Follow the candidate README and Quickstart,
  once from the terminal and once from the documented agent prompt in
  the project checkout. Verify each reaches its first integrated task.
  Record the starting URL, docs revision, runtime and plugin version
  when applicable, and landing evidence in the handoff. Clearly
  distinguish candidate documentation from documentation already
  published at the tag. Document the post-publication smoke check for
  the next release, which is outside this task's execution.

The README and Quickstart on main refer to the guide command introduced
after v0.9.1 while installing v0.9.1. Task 243 tested a candidate CLI
and candidate documentation together. This task checks the actual
published installation path and removes unnecessary choices and
directory assumptions for first-time users.

release metadata, publishing a release, and applying host setup to the
maintainer's real home directory.
