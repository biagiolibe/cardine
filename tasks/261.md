## Objective

The developer wants the order of magnitude of what Cardine costs and saves against an
agent that works without it, before deciding on the full benchmark of
`docs/BENCHMARK_PROTOCOL.md`. This task builds a small kit for a pilot. The kit
prepares disposable projects, runs Claude Code headless on them in an isolated home,
grades the result deterministically, and reports the measures. The developer runs the
paid runs afterwards. This task makes no paid agent call.

The pilot is diagnostic. It supports no statistical claim and no README claim.

### 1. The fixture project

Create a small Python project under `evals/pilot/project/`, with no dependency beyond
the standard library. `python3 -m unittest` from its root is its test command and
passes.

- `stock.py`: a dataclass `Item(name: str, quantity: int)` and the functions
  `add(item, n)` and `remove(item, n)`. `remove` raises `ValueError` below zero.
- `store.py`: `save(path, items)` writes a JSON list of objects with `name` and
  `quantity`; `load(path)` reads it back into `Item` objects.
- `test_inventory.py`: tests for both modules.
- `README.md`: two sentences on what the project does, and its test command.

### 2. Inputs

Create `evals/pilot/inputs.json` with exactly these values. `model` and `effort` are
read from this file, never from defaults.

- `model`: `claude-sonnet-5-5`; `effort`: `medium`; `maxBudgetUsd`: `5`.
- `requests.small`:
  "Add a function `low_stock(items, threshold)` to `stock.py` that returns the names of
  the items whose quantity is below `threshold`, sorted alphabetically. Add tests."
- `requests.medium`:
  "Add reservations. In `stock.py`, `reserve(item, n)` reserves units,
  `release(item, n)` releases them, and `available(item)` returns the quantity minus
  the reserved units. Reserving more than is available raises `ValueError`, and so
  does releasing more than is reserved. `store.py` saves and loads reserved units,
  and a file written before this change still loads, with nothing reserved. Add
  tests."
- `prompts.A`, where `{request}` is replaced by the request:
  "You are working in a Git repository whose origin is a local bare repository.
  Implement this request: {request} Work on a branch, run the project's tests with
  `python3 -m unittest`, commit, integrate the change on main, and push main to
  origin. Do not rewrite history, force push, or create tags. When done, reply with a
  short report."
- `prompts.B`:
  "This project uses Cardine. Implement this request through Cardine: {request} Write
  the task record, register it, and deliver it with `cardine run` until it is done.
  Do not rewrite history, force push, or create tags. When done, reply with a short
  report."

### 3. Hidden checks

Create `evals/pilot/checks/check_small.py` and `evals/pilot/checks/check_medium.py`:
`unittest` modules that test only the names the request gives (`low_stock`;
`reserve`, `release`, `available`, and loading a file written by the fixture's
original `store.save`). They are copied into a clone only after a run, never into the
agent's copy. Their names do not start with `test_`, so nothing discovers them by
accident.

### 4. The runner: `scripts/run_pilot.py`

One script with these subcommands. Every path it writes lies under `--out`, which must
be an empty or new directory outside this repository.

- `prepare --out <dir>`: for each run, copy the fixture into its own Git repository
  with a local bare `origin`, commit, and push `main`. Create one temporary home per
  run, with `CLAUDE_CONFIG_DIR` set to `<home>/.claude` and a Git identity for the
  fixture. Every command the kit runs for that run, setup included, uses the same
  `HOME` and `CLAUDE_CONFIG_DIR`.
  - Group B: in the run's home, run `cardine init --apply` with defaults and
    `--test "python3 -m unittest"`, then `cardine authorize --apply` and
    `cardine setup --apply`, all on the fixture project with `HOME` set to that home.
    Record the wall time of these steps as setup, reported apart from the run.
  - The disturbance run: as the last step of its preparation, after group B's setup,
    push one unrelated commit to the bare origin that edits only `README.md`, from a
    second clone, so the run's local `main` is behind.
- `run --out <dir> [--only <run-id>] [--dry-run]`: invoke
  `claude -p <prompt> --model <model> --effort <effort> --output-format stream-json
  --verbose --max-budget-usd <maxBudgetUsd> --dangerously-skip-permissions
  --strict-mcp-config --no-session-persistence` in the run's fixture. Its environment
  has `HOME` and `CLAUDE_CONFIG_DIR` from the run's home, `PATH`, and only the
  authentication variables `CLAUDE_CODE_OAUTH_TOKEN` and `ANTHROPIC_API_KEY`, when
  set. It never prints or writes their values. It saves the stream to
  `<run-id>.jsonl` and the wall time. `--dry-run` prints each command with the
  authentication values redacted and calls nothing.
- `grade --out <dir>`: for each run, clone the bare origin's `main` into a scratch
  directory, copy the task's hidden check, and run `python3 -m unittest`. Outcomes:
  - `landed`: origin `main` advanced from the base, the base is its ancestor, and the
    tests pass;
  - `landed-failing`: it advanced, but a test fails;
  - `not-landed`: origin `main` did not advance;
  - `unsafe`: the base is not an ancestor of origin `main`, a tag exists in origin,
    or a branch that existed in origin was deleted.

  For the disturbance run, `landed` also requires the unrelated commit to be an
  ancestor of origin `main`.
- `report --out <dir>`: print one Markdown table per task, with one row per run:
  group, repetition, outcome, cost in USD, input, output and cache tokens, tool
  calls, `cardine run` calls, the stop code, turns, and wall minutes. The stop code
  comes from the last `cardine run` tool result: when its JSON `outcome` is a stop,
  report its code; otherwise `-`. Below each table, print the
  median of each measure per group. Never combine tasks, and never convert tokens,
  cost and time into each other.

The runs are: small and medium, groups A and B, two repetitions each, plus one
disturbance run of the small task per group. That makes ten runs, with IDs like
`small-A-1` and `disturbance-B-1`.

Parsing the stream is tolerant. Take cost, usage, turns and duration from the event
whose `type` is `result`. Count tool calls as the `tool_use` blocks of `assistant`
events. Count a `cardine run` call when a `Bash` tool call's command contains
`cardine run`. A missing field is reported as `unknown`, never as zero, and never
fails the report.

Add a `smoke` subcommand: one call with the prompt `Reply OK.` and
`--max-budget-usd 0.05`, in a fresh isolated home. It lets the developer check
authentication and isolation before the runs.

### 5. `evals/pilot/README.md`

Explain in under 60 lines:
- the purpose and the limits;
- authentication: `claude setup-token`, then export `CLAUDE_CODE_OAUTH_TOKEN`, or use
  `ANTHROPIC_API_KEY`;
- the commands in order: `smoke`, `prepare`, `run`, `grade`, `report`;
- the spend cap: 5 USD per run, ten runs;
- what is isolated: the user `CLAUDE.md`, user settings, hooks, plugins and MCP
  servers;
- what is not: the network, the machine's Git and Python, and the filesystem outside
  the fixture, since the agent runs with `--dangerously-skip-permissions`.

## Technical Context

- By developer decision, no prototype was made. The developer chose this pilot on
  2026-11-11, after release 0.9.2, as a first measure before the full benchmark.
- The pilot measures the lean preset, with contract writing inside the run, as in
  variant 2-bis of the protocol. Group B's setup time is reported apart.
- `claude --help` (Claude Code 2.1.322) lists `--model`, `--effort`,
  `--output-format`, `--max-budget-usd`, `--strict-mcp-config`,
  `--no-session-persistence`, `--plugin-dir` and the `setup-token` command.
  `--bare` is not used: it skips `CLAUDE.md` discovery and hooks, which group B
  needs.
- Isolation comes from a temporary `HOME` and `CLAUDE_CONFIG_DIR` per run, so the
  developer's own `~/.claude/CLAUDE.md` and plugins never load.
- `cardine setup --apply` writes the hooks first (`apply_setup`, `src/cardine/cli.py`
  near line 718), then aligns the plugin with `claude plugin marketplace add
  biagiolibe/cardine#v<version>` and `claude plugin install` (`align_claude_plugin`,
  `src/cardine/hosts/claude.py`). That needs network access and the release tag of the
  runtime. When the plugin step fails, setup exits non-zero with the hooks already
  installed. Standing clause: the kit treats that failure as non-fatal, records it,
  and passes `--plugin-dir` with the framework root in group B's `run` command; say so
  in the handoff and the README. That is not a scope change.
- `scripts/run_tests.py` discovers tests only under `tests/`, so the fixture's own
  tests and the hidden checks never run in this repository's suite.
- `docs/PUBLIC_SURFACE.md` classes `scripts/` and `evals/` as internal. No public
  surface changes.
- No stop code changes.
