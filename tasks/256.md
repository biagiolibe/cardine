## Objective

Task 255 left two loose ends. This task closes both and adds no new behaviour.

### 1. No verified delivery record rewritten in place

`rebase_delivery` in `src/cardine/integration/refresh.py` rewrites the finished delivery
operation so that its `base` becomes the merged `main` commit. It keeps
`result: verified` on a record that was never verified against that base.
`deliver_implementation` in `src/cardine/lifecycle/delivery.py` needs this only because
it refuses a delivery operation whose `base` differs from the current one.

- **Remove the rewrite.** Delete `rebase_delivery` and its call in `record_base`. After a
  refresh, nothing in `refresh.py` writes the delivery operation.
- **Change the acceptance rule.** In `deliver_implementation`, a delivery operation with
  a different `base` is accepted only when all of these hold:
  - its `result` is `verified`;
  - its `base` is an ancestor of the current base (`git merge-base --is-ancestor`);
  - every other ownership check passes, as today.

  It is then treated like a stale verified delivery today: `intent = None`, and a new
  delivery operation is created for the merged head.
- **Refusals stay.** A pending operation with a different base, or a base that is not an
  ancestor, is still refused with «delivery operation owner or authority changed».

### 2. A stop message that does not contradict itself

`require_authority` in `src/cardine/lifecycle/receipts.py` always starts its message with
«developer reauthorization required: project/runtime/policy changed;», then appends the
detail from `_authority_difference`. When that detail ends with «Authorizing cannot
resolve this», the message contradicts itself.

- Start the message with «developer reauthorization required: » only when the detail
  sends the person to `cardine authorize`.
- Otherwise start it with «task checkout policy differs from the accepted policy: ».
- Keep the details of `_authority_difference` as they are.
