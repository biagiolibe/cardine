## Objective

Every task runs its Validation section twice: once as task validation, then again on the
candidate. `resolve_task_contract` in `src/cardine/tasks/contract.py` appends the record's
command IDs to `validation.baseline`, and `project_validation_commands` in
`src/cardine/shared/project.py` composes the candidate as baseline plus
`validation.candidate[<outcome>]`.

A validation is worth running when it can give a new result:

| Outcome | What is known | Candidate runs |
|---------|---------------|----------------|
| `REUSE` | Current `main` is the validated base: the code is the validated code, and only the records of the closure differ | The project's baseline and `candidate.REUSE`, **without the record's commands** |
| `BOUNDED` | `main` advanced on paths the task did not change: the tree is new | Unchanged, the record's commands included |
| `FULL` | `main` advanced on paths the task also changed | Unchanged, the record's commands included: a record may name a command outside the project's full set |

Change:

- `resolve_task_contract` adds a contract field `taskValidation`, the list of the record's
  command IDs that it appended to the baseline. A record command already in the project's
  baseline is not listed.
- `project_validation_commands(configuration, "REUSE")` leaves out the IDs in
  `configuration.get("taskValidation", ())`. A contract frozen before this task has no
  field, so it behaves as before. Every other call is unchanged, and task validation
  still runs the whole baseline.
- `schemas/task-state-v1.schema.json` gains the optional property. `.cardine/project.json`
  does not: `parse_project_declaration` keeps refusing it as an unknown key.

The second defect is the default for a project without CI.
`proposed_candidate_validation_declaration` in `src/cardine/integration/evidence.py`
proposes the test command only for `FULL`, so a project with no CI lands most tasks
without ever running its suite. When `tests/` exists and the project's `ci` is absent or
`none`, `BOUNDED` proposes the test command too. A project with CI keeps the current
proposal, because CI owns the full suite there.

In `docs/ADR_CARDINE_1_0.md`, decision 11, add an amendment dated 2026-11-08 after the
landing-mode table: each validation must be able to give a new result (the table above);
the project chooses one owner for the full suite: the candidate without CI, CI with
`ciBeforeLanding`, the pull request's required checks in `pull-request` mode.

## Acceptance Criteria

- [ ] With outcome `REUSE`, the candidate runs neither `task-tests` nor another record
  command, and still runs the project's baseline, `candidate.REUSE` and `git diff --check`.
  A test in `tests/test_run_integration_decision.py` checks it through `candidate_needs`.
- [ ] With `BOUNDED` and `FULL`, the candidate still runs the record's commands. The same
  test checks it.
- [ ] A contract without `taskValidation` composes exactly as before. A test in
  `tests/test_single_workflow_config.py` checks it.
- [ ] `tests/test_ci_evidence.py` checks the proposal with and without CI.
- [ ] `.cardine/project.json` with a `taskValidation` key is refused.
- [ ] Only the files under Relevant Files are edited, together with this task's own
  record, handoff, and state.
- [ ] **Task validation.** After the implementation commit, `cardine run` measures the
  commands under Validation and records the results in the handoff. Never edit the
  handoff after `cardine run` has written it, and commit nothing after the candidate is
  staged.
- [ ] Every command under Validation passes.
