### 1. Record the probe results

The probe writes to GitHub: it creates a scratch repository, opens a pull request and
pushes a merge. **The developer runs it, not the implementer.** Before this task starts,
the developer runs the commands below and pastes their whole output into the session.
If that output is not in the session, stop with `BLOCKED` and ask the developer for it.
Run none of these commands yourself.

    gh repo create cardine-forge-probe --private --add-readme --clone
    cd cardine-forge-probe
    git switch -c task-probe
    echo probe > probe.txt && git add probe.txt && git commit -m "Probe change"
    git push -u origin task-probe
    gh pr create --head task-probe --title "Probe" --body "Forge probe"
    gh pr review 1 --approve --body "self approval"            # G5: expect a refusal
    gh pr review 1 --request-changes --body "self changes"     # G5: expect a refusal
    gh pr review 1 --comment --body "author comment"           # G1: a COMMENTED review
    gh api repos/{owner}/{repo}/pulls/1/reviews                # G1, G6
    gh auth status                                             # G6: token scopes
    git switch main && git merge --no-ff task-probe -m "Integrate probe" && git push origin main
    gh pr view 1 --json state,mergedAt,closedAt,mergeCommit    # G4
    cd .. && gh repo delete cardine-forge-probe --yes          # needs the delete_repo scope

The last command needs the `delete_repo` scope (`gh auth refresh -s delete_repo`). If
that scope is missing, the developer deletes the repository from the GitHub settings
page. That step is not evidence.

Write `docs/FORGE_PROBE.md`. It records the date, the `gh` version and, for G4, G5 and
G6, the command, the observed result and one of the verdicts `confirmed`, `refuted` or
`inconclusive`. Copy no account login, token or private repository name into it: write
`<owner>` instead. Keep the review JSON to the fields `id`, `state`, `commit_id`, and
`user.login` as `<owner>`.

Then re-read the GitHub pages cited for G1, G2 and G3 in the ADR's External facts table,
and record for each whether the page still states the fact. The ADR says that the spike
fetched no page.

### 2. Update the ADR's fact marks

In the External facts table of `docs/ADR_REVIEW_VERDICT_SOURCES.md`, change the mark of

Nothing else in the ADR changes. A refuted fact that changes a reading rule stops the
task with `BLOCKED` and a short note for the developer. Do not rewrite the Decision.

### 3. The read-only client and the reading rules

Add `src/cardine/review/forge.py` with:

- `read_pull_request(root, branch)` reads the open or closed pull request whose head is
  the task branch on the repository of `origin`, and returns its number, author login,
  head SHA and state. It uses `remote_repository` from `src/cardine/integration/ci.py`
  for the repository, and calls `gh api` with explicit `--hostname`, as `ci.py` does.
- `read_reviews(root, number)` reads every page of the pull request's reviews, at most
  ten pages, and returns `id`, `user.login`, `state`, `commit_id` and `body` for each.
- `current_login(root)` returns the login of the `gh` account (`gh api user`).
- `forge_verdict(reviews, *, head, excluded_logins)` is a pure function. It applies
  rules 1 to 5 of "Reading the verdict" in the ADR, in that order, and returns the
  verdict (`APPROVE`, `CHANGES_REQUESTED` or none), the deciding review, and whether
  an `APPROVED` or `CHANGES_REQUESTED` review was dropped by rule 2, which means stale.

The functions only read. A missing `gh`, a refused call or a non-JSON answer raises
`CardineError` with the `gh` error text, as `ci.py` reports refusals. No function
writes to GitHub, to the task state or to the worktree.

Add `tests/test_review_forge.py`. It tests the reading rules with in-memory review
lists, and the `gh` calls with `subprocess.run` patched. No test calls the real `gh`
or GitHub.
