## Objective

`cardine self-update` prints bare `Key: value` lines. It has no sections, no emphasis and
no progress while it reaches the network, fetches Git objects or runs pipx. At the end it
says only:
- "Restart running Codex and Claude Code sessions";
- "Run cardine upgrade --check in each project", for template-changing releases only;
- an `authorize` command for the one checkout named by `--project`.

It never says that every project needs `authorize`, that `upgrade --apply` and a commit
follow `upgrade --check`, or that `cardine doctor` confirms the result. The developer
wants an update that reads like a serious CLI tool.

### 1. A small terminal style module

Add `src/cardine/shared/terminal.py`, with no third-party dependency:

- **Styling** is on only when standard output is a terminal, `NO_COLOR` is unset and
  `TERM` is not `dumb`. Otherwise every helper returns plain text, so redirected output
  and tests stay clean.
- **Helpers:**
  - `section(title)`: a bold title line;
  - `step(index, total, label)`, then `done(detail)`, `skipped(detail)` or
    `failed(detail)`, rendered as `[2/4] Resolve release … ✓` with green, yellow or red
    marks;
  - `note`, `warn` and `error` lines;
  - `command(text)`, which highlights a command to copy.
- **`spinner(label)`** is a context manager. While a slow call runs, it redraws one line
  on standard error about every 100 ms, and it clears the line at the end. When styling
  is off it prints nothing.

### 2. `self-update` uses it

Restructure the human output of `run_self_update`, `_run_self_update`
(`src/cardine/release/update.py`) and `run_installer_update`
(`src/cardine/release/installer.py`) into three sections.

**Plan**
- current version, target version, release kind, release notes link;
- the installer, or the Git operation.

**Apply** (only with `--apply`), as numbered steps:
- resolve the release;
- fetch or reinstall, under a spinner;
- verify;
- align the Claude Code plugin.

The pipx or uv output is captured. It is shown only when the step fails.

**Next steps**, a numbered checklist:
1. Restart running Claude Code and Codex sessions.
2. In each project that uses Cardine, run `cardine authorize --check --project <checkout>`,
   then `cardine authorize --apply --project <checkout>`. When `--project` names a
   checkout, say whether that checkout holds a runtime acceptance that this update
   replaced; that is `stale_runtime_report`.
3. Only for a template-changing release: `cardine upgrade --check --project <checkout>`,
   then `cardine upgrade --apply --project <checkout>`, then review and commit the
   managed files.
4. `cardine doctor --project <checkout>` to confirm.

`--check` prints Plan and a short "Run `cardine self-update --apply` to update" line. It
does not print the checklist.

### 3. Errors

Every refusal of `self-update` prints one red `error` line with the cause. It is followed
by the `command` to resume, where a resume exists, or by the manual alternative from task
288. Stop codes, exit statuses and the JSON of stops do not change.

### 4. Documentation

Rewrite `docs/HOW_TO_UPGRADE.md` around the same three sections and the checklist. Show
one short sample of the plain output.

## Technical Context

- **Developer decision** (2026-11-12): the update must read like a serious CLI, with
  sections, color where emphasis helps, progress for slow steps, and explicit next steps.
- Human-readable output is never stable (`docs/PUBLIC_SURFACE.md`), and `self-update` is
  experimental, so the text may change freely.
- Task 288 changes `update.py` and `installer.py` first; this task builds on it.

  `python3 scripts/run_tests.py --parallel --module <name>`.
