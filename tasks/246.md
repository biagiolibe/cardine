# Task 246 — Recover when task records have not been committed

> **ID**: `246`
> **Category**: Fix
> **Priority**: 🟠 P2
> **Estimate**: ~2h
> **Assigned to**: unassigned
> **Session**: First task onboarding, 2026-11-10
> **Origin**: friction

## Objective

Catch a locally registered task whose record or state is missing from
committed main before preparing its branch or worktree. Tell the agent
how to publish the registration and resume in the same session when
its existing permissions allow it.

## Acceptance Criteria

- [ ] A newly registered task with its record and state present only in
  the working tree is recognized by ID. Before creating a task branch,
  worktree, or preparation receipt, `cardine run` checks that the
  registered record and state are available at the commit from which it
  would prepare the task. A staged but uncommitted registration, or a
  registration committed only on another branch, does not satisfy the
  prerequisite. Preserve existing diagnostics for invalid state.
- [ ] If publication is the only missing prerequisite, the run result
  identifies the affected paths and main, explains how to stage and
  commit the registration, and supplies the exact command to retry
  afterward. Describe pushing when required by the project's workflow.
  Represent this as recoverable agent work, without a human-decision
  stop, misleading unknown-identity error, or retry loop. The agent can
  finish the authorized Git steps and continue in the same session.
  Cardine does not silently commit, push, expand Git permissions, or
  bypass an actual host denial.
- [ ] For that queued task, status text and JSON show that it is not
  startable yet and distinguish an uncommitted registration from an
  unmet dependency. Status remains read-only by default. Once the
  registration is committed to main, the prerequisite clears. Keep
  status, read-only run preview, and actual run consistent.
- [ ] Reproduce the VM sequence in an isolated Git fixture with a
  writable local bare origin: start from configured main, register
  task 001, and invoke run before committing either record. Verify the
  recovery result and absence of a task branch, worktree, or preparation
  receipt. Commit and publish only the registration, retry the returned
  command, and verify that normal preparation and implementation begin
  in the same flow without manual receipt, worktree, or authority repair.
- [ ] Document the recovery result and how a caller follows it. Existing
  committed registrations and genuine human-decision stops continue
  to behave as before.

## Technical Context

The v0.9.1 VM walkthrough registered task 001 in the primary checkout,
but the two registration files remained untracked. Status reported the
task as startable. Run created a task worktree at the old main commit and
then reported COMMAND_REFUSED with unknown task identity in the worktree
step. The response required a human decision even though publishing the
registration was the normal next step. The new guard must use committed
Git inputs and run before preparation has effects.

## Out of scope

Changing task creation to commit or push automatically, repairing worktrees
or receipts left by older runtimes, changing permissions or authorization
policy, and changing the released v0.9.1 onboarding evidence for task 245.
