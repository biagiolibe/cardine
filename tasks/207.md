## Objective

`python3 scripts/run_tests.py --parallel --clean-clone` runs for several minutes and
prints nothing until it ends:

- `run_shards` writes each shard's output to a private file and waits for the shards in
  order, so nothing is reported when a shard finishes;
- `run_clean_clone` runs `scripts/check_repository.py` and the inner parallel suite with
  `capture_output=True` and prints their output only when each step has ended.

The developer watches validations through Cardine's live view (task 208) and sees no
sign of progress during the longest command a task runs. This task makes the runner
report progress as it happens, on stderr only, so that the summary on stdout, which
tests and the agents read, does not change.

After this task:

- a parallel run prints, on stderr, one line when it starts the shards and one line each
  time a shard finishes, in the order the shards finish;
- a clean-clone run prints, on stderr, one line after the clone and one line before and
  after each step, and lets the inner parallel run's stderr through as it is written, so
  its shard lines appear live.

The lines look like this (wording may vary; the facts must be there):

```text
run_tests: 2179 tests in 8 shards
run_tests: shard 3/8 finished in 41.2s: exit 0, ran=270 failures=0 errors=0
run_tests: shard 5/8 finished in 12.0s: exit 1 without a result
run_tests: clean-clone: cloned 0f5dbc7
run_tests: clean-clone: scripts/check_repository.py started
run_tests: clean-clone: scripts/check_repository.py exit 0 in 18s
```

## Acceptance Criteria

- [ ] A parallel run writes one start line and one line per shard to stderr, each flushed
  when it is written. Each shard line names the shard, its exit status, its time and,
  when the shard printed a result, its `ran`, `failures` and `errors` counts. A test in
  `tests/test_run_tests.py` checks it.
- [ ] A shard's line is written when that shard finishes, not after every shard has
  finished. A test checks it, for example with a suite where one shard is slower than
  the others and its line comes last.
- [ ] stdout is unchanged: the existing tests that count stdout lines and compare
  `stable()` outputs pass unedited.
- [ ] A clean-clone run writes the clone line and the step lines to stderr, and the inner
  parallel run's shard lines reach the outer stderr before the run ends. Its last stdout
  line is still `clean-clone commit=… total=… digest=… outcome=…`. A test checks it.
- [ ] `--shard`, `--list`, and the refusals (usage errors, dirty tree, unreadable failure
  record) print no progress lines.
- [ ] The report of failed shards, the `PARTIAL` line, the failure record and the
  coverage proof are unchanged.

  own record, handoff, and state.
- [ ] Every source and test file stays below 1,500 lines.
- [ ] **Task validation.** After the implementation commit, `cardine run` measures the

## Technical Context

- Write every progress line with `print(..., file=sys.stderr, flush=True)`. The
  existing summary stays on stdout.
- `run_shards` must keep returning its results in shard order: the report of failed
  shards depends on it. Only the waiting changes: poll the processes (for example
  `process.poll()` every 0.1 s) or wait in threads, report each one as it finishes, then
  return the results in order. `parse_shard_output` already gives the counts.
- In `run_clean_clone`, the inner steps keep `stdout=subprocess.PIPE` (the coverage proof
  is read from it), but stderr is inherited instead of captured, so the inner run's
  progress lines pass through live. The inner stdout is printed after each step, as now.
- Cardine stores a validation command's stderr in its evidence, bounded, and never in the
  JSON an agent reads. An agent that runs the suite by hand during development sees
  about ten more lines per run.
- The project's standing decisions are in `PROJECT_WORKFLOW.md`, section `Standing
  decisions`.
