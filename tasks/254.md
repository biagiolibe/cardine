# Task 254 — Wait for required CI within one run invocation

> **ID**: `254`
> **Category**: Feature
> **Priority**: 🟠 P2
> **Estimate**: ~2h
> **Assigned to**: unassigned
> **Session**: Delivery workflow, 2026-11-11
> **Origin**: Repeated model calls while waiting for CI

## Objective

1. When `cardine run` reaches the direct landing gate `ciBeforeLanding`,
   let the same process poll the required checks until they pass, fail, or
   the wait budget expires. Use a default budget of 900 seconds and expose
   `--ci-wait-seconds <seconds>` for faster or slower projects. Accept
   nonnegative integer seconds. A value of zero performs one status query
   and returns using the current polling behavior. Other lifecycle waits
   and tasks without this CI gate retain their behavior.
2. Poll the existing repository, ref, delivered SHA and required check set.
   Keep the current push and receipt behavior. Sleep outside integration
   leases and writer locks. Apply a monotonic deadline to the waiting phase,
   including provider queries, and cap each request and sleep by its
   remaining budget.
3. Emit one existing-schema JSON result. Return the ordinary next step on
   success and the ordinary implementation iteration on CI failure. At
   timeout, return `waiting` with a short diagnostic that names the pending
   checks, delivered SHA and expired wait budget. Include the exact
   `next.command` for another `cardine run` invocation with the same wait
   budget. The timeout does not cancel or restart CI, consume a validation
   retry, or require a human decision. A later invocation starts a fresh
   wait window on the already-published SHA if the delivery is unchanged.
4. Document the default, override, zero mode and retry behavior in the
   output section of `docs/RUN_COMMANDS.md`. Keep the wait budget a runtime
   option.

## Acceptance Criteria

- [ ] A fake clock and fake provider show pending checks turning green or
  failing during one invocation. The CLI emits one final JSON envelope,
  without per-poll output. Success and failure keep their existing
  outcome and evidence semantics.
- [ ] On timeout, the CLI returns `waiting` with a positive retry interval
  and the complete next command. Repeating it for the unchanged delivery
  checks the same SHA without another push, a new CI run or a validation
  failure count. The same behavior holds after interrupting a wait.
- [ ] A check for another SHA never satisfies the gate. If delivery, task
  state or the required checks change during the wait, an old result cannot
  authorize landing. Preserve the existing receipt and remote-ref checks.
- [ ] A stalled or paginated provider cannot make the poll phase exceed its
  deadline by starting unbounded requests. Waiting does not hold a writer
  lock or integration lease, and another task can integrate while this
  task is waiting.
- [ ] Tests cover default, longer, shorter, zero and invalid CLI budgets.
  Disabled CI and other waiting paths keep their existing behavior. Tests
  use an injected clock, sleep and provider or local fixtures.
- [ ] The repository checks and targeted validation pass.

## Technical Context

- By developer decision, no prototype was made.
- The current engine returns a ten-second retry interval for CI. Move
  repeated status queries into the CI wait phase. Preserve single-probe
  behavior for internal callers that rely on it.
- Preserve the task's frozen CI policy, check evidence and ownership
  protocol. A timeout is an elapsed wait budget, separate from the result
  of the check. Reuse the existing waiting outcome and JSON schema.
- The planned run parser, CI step and output documentation changes are
  separate from task 249's stop diagnostic and recovery text and from the
  onboarding command changes.
