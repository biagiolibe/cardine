# Task 258 — Make guide, setup and the bare command point the way

> **ID**: `258`
> **Category**: Fix
> **Priority**: 🟠 P2
> **Estimate**: ~2h
> **Assigned to**: unassigned
> **Session**: Onboarding navigation, 2026-11-11
> **Origin**: friction

## Objective

A new user who gets lost has no reliable «you are here».

- `cardine guide` still says to choose between init and adopt, which `init` now does
  itself.
- `guide` points to `docs/QUICKSTART.md`, a file that does not exist in the user's
  project.
- After configuration, `guide` prints raw Python dictionaries.
- A bare `cardine` prints an argparse error.
- `cardine setup --check` prints about thirty detail lines with no summary.
- On a project that is not configured, `setup` proposes, and `--apply` writes, a project
  declaration with stale values. Its `locations.plan` is `PROJECT_PLAN.md`, which task 238
  removed, and its name differs from the default that `init` uses.

Make these edits.

### 1. `cardine guide`, before configuration

In `src/cardine/shared/project_guide.py`, the `bootstrap` section becomes exactly these
entries. `<project>` is described in part 3.

1. `This checkout is not configured for Cardine yet.`
2. `Run cardine init<project>. It chooses between initialization and adoption, proposes every choice with a default, and asks before writing or publishing anything.`
3. `If no test command is detected, add --test "<command>".`
4. `Then run cardine guide<project> again.`

Its `references` become one entry: the quick start URL of part 3.

### 2. `cardine guide`, after configuration

The `first_task` section becomes exactly these entries, in this order:

1. `Connect your agent: preview with cardine setup --check<project>, then run cardine setup --apply<project> from your terminal.`
2. `Check the host with cardine doctor --host claude<project> or cardine doctor --host codex<project>.`
3. `Ask your agent for a task, or write one from tasks/TASK_BLUEPRINT.md and register it with cardine task new <ID> --record <file><project>. Commit and push the record on main.`
4. `Deliver it with cardine run <ID><project>, following each next command until done.`

The `choices` section becomes one readable line per fact, with no Python or JSON
literals:

- `Preset: <preset>. Review: <required|not required>. Authority: <required|optional>.`
- `Validation: <id> runs <command>`, with one `; `-separated pair for each declared
  command, or `Validation: not declared; run cardine init` when none is declared.
- `CI before landing: yes (<provider>, checks: <comma-separated checks>)`, or
  `CI before landing: no`.
- `Console: cardine console<project>.`

The text renderer titles the sections `Next steps`, `This project` and `References`.

`--format json` keeps its keys (`version`, `project`, `facts`, `sections`) and its section
keys (`bootstrap`, `first_task`, `choices`, `references`). Only the strings change.

### 3. Paths and links in guide

- `<project>` is empty when the current directory is the project root. Otherwise it is
  ` --project <shell-quoted path>`.
- The quick start reference is
  `https://github.com/biagiolibe/cardine/blob/v<version>/docs/QUICKSTART.md`, where
  `<version>` is the running framework version from `read_version` in
  `src/cardine/release/version.py`.
- References that name files of the user's project, such as `tasks/TASK_BLUEPRINT.md`,
  stay as they are.

### 4. A bare `cardine`

`cardine` with no arguments prints this text to standard output and exits 0. The top
level `cardine --help` prints it as its epilog.

```text
Everyday commands:
  guide        where this checkout stands and what to do next
  init         configure this project (interactive on a terminal)
  setup        connect Claude Code or Codex (--check, then --apply)
  run          deliver a task, one step per call
  status       task status
  doctor       check a host
  self-update  update Cardine
Run `cardine guide` when unsure.
```

Every subcommand stays listed and callable. Nothing in `docs/PUBLIC_SURFACE.md` changes
tier.

### 5. Interactive init names the next step

At the end of a successful interactive `cardine init`, whether or not the configuration
was published, print `Next: cardine guide<project>` as the last line. This matches the
non-interactive `init --apply`.

### 6. `cardine setup` on a project that is not configured

In `plan_setup` in `src/cardine/hosts/setup.py`, when `.cardine/project.json` does not
exist, Cardine proposes and writes no project declaration. The state line becomes
`project-declaration: missing; run cardine init first`, and no
`project-declaration-proposal` line is printed. All user-level and host changes are
planned as today. The `advisory-incomplete` case, a declaration that lacks `project`, is
unchanged.

### 7. A summary at the top of `cardine setup --check`

Before the existing detail lines, print:
- `changes on --apply: <n>`;
- one `- <change>` line for each entry of the plan's `changes` list, in order;
- `next: cardine setup --apply` when `n` is greater than 0, or `nothing to change`
  otherwise.

The detail lines that follow are unchanged.

## Technical Context

- By developer decision, no prototype was made.
- The coordinator checked these behaviours on `main` at `6a011da`, in a fresh repository
  with a temporary `HOME`:
  - `setup --check` before `init` proposes `"plan": "PROJECT_PLAN.md"` and the name
    `Fresh 517F8764Ba29`, while `init --check` proposes `fresh`;
  - `guide` before `init` prints the init-or-adopt sentence;
  - a bare `cardine` exits 2.
- Tests that expect setup to write a project declaration in a project that is not
  configured must change. `test_host_repeatability` lists `file:project-declaration` among
  the effects of the default and custom-root cases. Update them, and any other host-setup
  test with the same expectation, to the behaviour of part 6, and name them in the
  handoff. That is not a scope change.
- The surface exceeds ten files only through host-setup tests that share the expectation of part 6; the production change is four files.
- Human-readable output is not a stable interface (README, Documentation): changing it is
  allowed. JSON keys are stable.
- No stop code changes. If an emitter moves, add its `EMITTER_CAUSES` row in
  `src/cardine/stops/causes.py`; that is not a scope change.
- This task precedes task 259, which documents this behaviour, and the 0.9.2 release.
