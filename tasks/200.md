# Task 200 — Register hook commands that run outside an interactive shell

> **ID**: `200`

> **Session**: Switch follow-ups, 2026-11-08

## Objective

On 2026-11-08 the implementer of task 198, running in Codex from the desktop app, saw
on every tool call:

```text
• Hook failed
  └ hook exited with code 127
```

`setup` registers each hook as the bare text `cardine hook <name> --host <host>`. The
host runs that text through a shell. A host started from a desktop app does not inherit
the developer's interactive shell, so `cardine` is not on its `PATH`, and the command is
not found. The read guard and the stop audit then silently do not run. On the same
machine a bare `python3` resolves to the system Python 3.9, which the launcher refuses,
so putting `cardine` on that `PATH` alone would not be enough.

`doctor` did not notice: `probe_hook_invocation` looked the command up with
`shutil.which` in the doctor's own environment, which is the developer's interactive
shell, and reported `ready`.

This task:

1. registers each hook with absolute paths, the interpreter that runs `setup`
   (`sys.executable`) and the `bin/cardine` launcher of the running checkout, through a
   new `hooks.launcher()`. It falls back to the bare `cardine` when the running code has
   no launcher next to it;
2. recognizes a registration as Cardine's own by its shape, `<…/cardine> hook <name>
   --host <host>`, through `hooks.owns`, instead of by exact text. A rerun of `setup`
   therefore replaces an old bare registration instead of adding a second one, and moves
   the registration when the interpreter or the checkout changes;
3. makes the doctor probe run the registered text as a desktop host does: through
   `/bin/sh -c`, with only `HOME` and the base macOS `PATH` (`/usr/bin:/bin:/usr/sbin:/sbin`).
   Exit code 127 becomes `unverified: the registered hook command does not resolve
   outside an interactive shell; rerun setup`.

## Technical Context

- `hooks.launcher()` finds the launcher at `Path(__file__).resolve().parents[3] /
  "bin/cardine"`, the same checkout root that `receipts.runtime_digest_once` measures.
- `sys.executable` is the interpreter that runs `setup`. If Homebrew later replaces it,
  the doctor probe reports `unverified` and a new `setup` run moves the registration.
- Task 197 also edits `src/cardine/hosts/setup.py`, in different functions: its hunks
  are in `PinnedSetupPlan`, `_plan_inputs`, `plan_setup`, `print_setup_plan`, and
  `apply_setup`; this task edits only the import line and `probe_hook_invocation`.
- The project-level `.codex/hooks.json` of this repository still holds bare duplicates.
  `setup` reports them as advisories; removing them is a separate task.
- During development, run only what the change touches: `python3
  scripts/run_tests.py --parallel --module <name>`, repeating `--module`. Do not run
  `python3 -m unittest` directly. Run the full suite once, as the counted
  clean-clone validation.
- Run validation suites one at a time and redirect each one's output to a log file
  with its exit code appended, so the result survives a lost process handle.
- Other tasks share this machine. Stop only your own processes, by process ID;
  never `pkill` test runs by pattern.
