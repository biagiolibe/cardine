# Task 255 — Bring the task branch up to date with main before CI

> **ID**: `255`
> **Category**: Feature
> **Priority**: 🟠 P2
> **Estimate**: ~2h
> **Assigned to**: unassigned
> **Session**: Validation ownership, 2026-11-11
> **Origin**: friction

## Objective

With `ciBeforeLanding`, CI validates the task branch head. When `main` advances during
delivery on paths that the task also changed, `decide_integration_validation` in
`src/cardine/integration/decision.py` returns `FULL`. The combined tree then needs a
full run, which either repeats the suite locally while the integration lease is held, or
happens only after the push to `main`. The ADR (decision 9, amendment of 2026-11-08) gives
the full suite one owner: CI.

Make CI validate the tree that will land. When the integration decision would be `FULL`
and the contract has `ciBeforeLanding`, Cardine first merges the current `main` into the
task branch, so that CI and the candidate both see the combined tree, and the candidate
becomes `REUSE`. This is the semantics of a branch that must be up to date before it
merges.

### 1. When to refresh

Before CI is requested or polled for the delivered head (`run_ci_step` in
`src/cardine/lifecycle/engine.py`), compute the same decision that staging computes in
`src/cardine/integration/merge.py`, from the same inputs. Do not duplicate the
computation: extract it into one function that both call. Refresh only when all of these
hold:
- the outcome is `FULL`;
- the contract has `ciBeforeLanding`;
- landing is `direct`.

`REUSE` and `BOUNDED` keep their current behaviour. Without `ciBeforeLanding`, nothing
changes.

### 2. The refresh

In the task worktree, Cardine runs `git merge --no-ff --no-edit main`, with the message
`Merge main into task-<ID>`. It never rebases or rewrites the branch.

- **Conflict.** Cardine aborts the merge and stops with the existing `INTEGRATION_CONFLICT`
  code. The resume tells a person to merge `main` into the task branch in the task
  worktree, resolve and commit, then run `cardine run <ID>` again. Agents never resolve
  textual conflicts.
- **Success.** The task's recorded base becomes the merged `main` commit. Use the same
  owned-receipt path that `repair_task_worktree_base` in `src/cardine/worktree/checkout.py`
  uses (`repair_preparation`).
  - Without this, `enforce_execution_scope` would count main's changes as task changes.
  - Without it, the measured validation's base would also not match the recorded base.
- **After a success.** Task validation must run again on the new head, followed by CI
  on that head, through the ordinary resolver path. Nothing is reused from the old head.
  The `run` output is an ordinary `next` with the action `refresh-from-main` and one
  diagnostic, which names:
  - the merged `main` commit;
  - the task paths that interacted with it.

### 3. Integration after a refresh

With the recorded base equal to the current `main`, `decide_integration_validation`
returns `REUSE`, and the candidate runs only the baseline and `candidate.REUSE`. If
`main` advances again before staging and the decision is `FULL` once more, the next
`cardine run` refreshes again. Each refresh is progress, not a retry, and consumes no
validation retry.

### 4. Documentation

In `docs/RUN_COMMANDS.md`, add the `refresh-from-main` action and one paragraph on when
it happens. In `docs/PROJECT_DECLARATION.md`, under `ciBeforeLanding`, add this sentence:
«When `main` has changed paths that the task also changed, Cardine merges `main` into the
task branch first, so CI validates the tree that will land.»

## Acceptance Criteria

- [ ] A disposable-project test (local bare remote, CI provider faked) shows the
  sequence:
  1. task A lands while task B is delivered;
  2. B's decision would be `FULL`;

  5. B's candidate is `REUSE`;

## Technical Context

- By developer decision, no prototype was made.
- This task depends on 254, which changes `run_ci_step`, `ci.py`, and `engine.py` to
  wait for CI inside one invocation. Build on the code that 254 lands. Do not restore the
  earlier behaviour.
- The developer removes the full suite (`adopt-ae1cbbf1076d9cc4`) from `candidate.FULL`
  in `.cardine/project.json` on `main` before this task starts. So, with
  `ciBeforeLanding`, no candidate ever runs the full suite locally. A task cannot land a
  change to `.cardine/project.json`: do not edit it.
- The refresh merge is a commit made by Cardine in the task worktree. It is not an
  implementation commit and must not be counted as an iteration.
- The new action `refresh-from-main` is a `next` outcome, not a stop: no person is needed
  unless there is a conflict.
- Standing scope clause: another caller of the decision inputs, or a status renderer that
  lists actions, may be updated and named in the handoff without a stop. That is not a
  scope change. A change to the stop registry beyond the resume text of
  `INTEGRATION_CONFLICT` is a scope change.
