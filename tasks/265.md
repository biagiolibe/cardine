## Objective

The 0.9.2 smoke test and a check on a consumer project found three defects in the
output of `cardine setup`:

- On a project whose Claude Code plugin is 0.9.1 while the CLI is 0.9.2,
  `cardine setup --check` prints `changes on --apply: 0` and `nothing to change`, and
  `claude-plugin: mismatch: plugin 0.9.1, CLI 0.9.2` further down. Yet
  `cardine setup --apply` does align the plugin (`src/cardine/cli.py` near line 720).
  The plan hides the one step that apply would take.
- After a change, `setup --apply` prints `result: updated; restart Codex`, also to a
  user who only runs Claude Code. It prints that line before the plugin step, so a
  `result: no-op` can be followed by `claude-plugin: aligned to v0.9.2`.
- `setup --check` prints the list of changes twice: at the top, under
  `changes on --apply: <n>`, and again at the bottom, under `changes:`.

### 1. The plugin step in the plan

In `plan_setup` (`src/cardine/hosts/setup.py`), where the plan's `claude_plugin` state
is computed, add the change
`align the Claude Code plugin to v<version>` to the plan's changes, where `<version>`
is the framework's version, when both hold:
- the plugin state is `absent` or starts with `mismatch`;
- `claude` is on `PATH`.

Read `PATH` through a parameter with a default of `shutil.which`, so that tests do not
depend on the machine's `PATH`. Add the change before the plan's inputs are computed,
so the count, the `next:` line and the pinned plan agree. Without `claude` on `PATH`
nothing changes: apply prints the commands to run, as today.

### 2. The result line

In `src/cardine/cli.py`, the `setup` branch runs the plugin step before it prints the
result, then prints:
- `result: updated; restart your agent so it loads the changes` when `apply_setup`
  changed something or the plugin step returned `aligned`;
- `result: no-op` otherwise.

The `claude-plugin:` line that `align_claude_plugin` prints stays, before the result.

### 3. One list of changes

In `print_setup_plan`, remove the trailing `changes:` block. The list under
`changes on --apply: <n>` stays.
