# Task 270 — Show a task started on its branch as in progress in status and the briefing

> **ID**: `270`
> **Category**: Fix
> **Priority**: 🟠 P2
> **Estimate**: ~2h
> **Assigned to**: unassigned
> **Session**: Consumer report after adoption, 2026-11-11
> **Origin**: friction

## Objective

A consumer reported this after adopting Cardine. The worktree of one task exists, with
a commit `Start task <ID>` and uncommitted work, yet `cardine status` and the per-turn
briefing say `in_progress=0` and list that task as startable.

The cause is that `cardine run` commits the transition to `in_progress` in the task
worktree, on the task branch (`run_worktree_step`, `src/cardine/lifecycle/engine.py`
near line 523). The transition reaches `main` only when the task is integrated.
`load_task_snapshot` (`src/cardine/tasks/status.py`) reads only the state files on the
primary checkout. The console already observes the branch
(`_branch_observation`, `src/cardine/console/snapshot.py` near line 240), so the console
and `cardine status` disagree.

`cardine run` itself is safe: it reads the worktree's state and resumes
(`engine.py` near lines 402 and 506). The risk is a second agent or person starting a
task that `status` calls free.

### 1. The branch observation

Add a module `src/cardine/tasks/branch_state.py` with one public function,
`observe_task_branches(project_root, model) -> dict`. For every row of the status
model whose status is not `done` or `cancelled`:

- resolve the task's canonical branch with
  `resolve_task_identity(project_root, task_id, "existing")` (`src/cardine/tasks/identity.py`);
- list the worktrees once, with `git worktree list --porcelain` and
  `parse_worktree_records` (`src/cardine/shared/git.py`);
- when a worktree of that branch exists and is a directory, read the task state file
  inside it (`state_path`, `src/cardine/tasks/state_core.py`);
- when only the branch exists, read the state file from `refs/heads/<branch>` with
  `git show`;
- validate the state as `load_task_snapshot` does. A missing, unreadable or invalid
  state on the branch is ignored for this task. It never raises and never writes.

It returns, per observed task, the branch status and its source:
`task state in worktree <branch>` or `task state on branch <branch>`.

### 2. Use it where status is read, not where it is written

In `cardine status` without `--write` (`src/cardine/cli.py` near line 648) and in the
briefing (`render_status_lines` and line 55 of `src/cardine/hosts/briefing.py`), apply
the observation to the model, with these rules:

- A branch status replaces the main status only when it is later in the order
  `queued`, `in_progress`, `in_review`, `done`. A branch never makes a task
  `cancelled`, and never moves a task back.
- A task whose canonical worktree exists while main says `queued` is shown as
  `in_progress`, as the console does (`snapshot.py` near line 688).
- A replaced row gets `startable: false` and a new field `source` holding the source
  string. The totals count the shown status.
- `render_task_status` prints `| source: <source>` at the end of a replaced row. The
  JSON output has the field, and rows that keep the main status have no `source`
  field.

`cardine status --write` (`write_views`), the console, adoption and every engine
reader keep reading main only. The generated queue must not depend on which
worktrees exist on one machine.

## Acceptance Criteria

- [ ] In a disposable project, a task started with `cardine run`, whose `in_progress`
  transition exists only on its branch, is shown as `in_progress`:
  - by `cardine status`, with `startable: false` and a source naming the worktree;
  - by the briefing, under `In progress:`, and not under `Startable:`.
- [ ] With the worktree removed and the branch kept, the source names the branch.
- [ ] A worktree prepared for a queued task, with no transition yet, shows
  `in_progress`.
- [ ] An invalid state on the branch leaves the main status and adds no diagnostic.
- [ ] A branch status earlier than main (`queued` on the branch, `in_review` on main)
  does not change the row.
- [ ] `cardine status --write` produces the same queue with and without the worktree.
- [ ] The briefing still imports no network module and writes nothing
  (`tests/test_cli_startup.py`).
- [ ] Only the files under Expected code surface are edited, together with this task's
  own record, handoff, and state.
- [ ] **Task validation.** After the implementation commit, `cardine run` measures the
  commands under Validation and records their results.
- [ ] Every command under Validation passes.

## Technical Context

- **Developer decision** (2026-11-11): fix this before the consumer starts concurrent
  tasks. The consumer has an ADR that allows tasks in parallel when they share no
  dependency, code surface or validated value.
- The observation is advisory display. It only lowers startability and raises the
  shown status; it never gates the engine. That is why reading unauthenticated
  branch bytes is acceptable here. The engine keeps its own reads.
  `docs/FORGERY_INVENTORY.md` classes `tasks/status.py` as a reader of local bytes.
- Duplicating the console's observation in a small reader is accepted for this task.
  Moving `_branch_observation` into a shared module is out of scope.
- `cardine status` is a stable command (`docs/PUBLIC_SURFACE.md` line 57). The
  optional `source` field is additive. No existing field changes name or meaning:
  `status` and `startable` still describe the task, now with what the branch
  shows.
- `tests/test_module_inventory.py` requires each module-level binding name to have
  exactly one definition: choose new names that no other module defines.
- `test_cli_startup` checks the briefing's imports and that it writes nothing. Git
  subprocesses are allowed; network modules are not.
- During development, run tests with
  `python3 scripts/run_tests.py --parallel --module <name>`, never
  `python3 -m unittest` directly.
- No stop code changes.
