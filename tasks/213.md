## Objective

The full suite on `main` at `93f2140` fails 7 tests that this task repairs; task 212
repairs the other 3. CI did not report any of this: `.github/workflows/validate.yml` sets
`continue-on-error: true`, so a run with failures is shown as a success (`fe929ee`: `FAILED
ran=2127 failures=8 errors=3`, conclusion `success`), and `cancel-in-progress: true` cancels
the run of every commit that a newer push follows. Until now the coordinator has run the
full suite by hand after a group of tasks. This task replaces that exception: CI runs the
full suite on the task commit, and `cardine run` lands only when it is green.

### 1. One engine fix

Since task 202 untracked files no longer make the primary checkout dirty, so `stage` in
`src/cardine/integration/merge.py` goes on when `recover_landing_residue` has left a
pending landing residue that it could not prove owned. A later write then stops with the
untyped `pending operation must be replayed before another write`. After the
`--untracked-files=no` check, `stage` raises
`stop_error("PRIMARY_DIRTY", "pending landing residue must be resolved before staging")`
when `receipts.pending_operation(project_root, identity.canonical_id)` is true. This makes
`test_foreign_dirt_beside_owned_residue_preserves_everything` and
`test_changed_residue_bytes_stay_dirty_and_are_preserved` in `tests/test_run_recovery.py`
pass unchanged.

### 2. Test expectations the integrated tasks made obsolete

- `test_dirty_primary_checkout_stays_a_guardrail` in `tests/test_run_recovery.py`: it
  creates an untracked `foreign.txt`. Modify a tracked file instead, keeping the expected
  stop (task 202).
- `test_delivery_commits_only_owned_projections_and_is_idempotent` and
  `test_commit_failure_reports_pending_actual_state_and_recovers` in
  `tests/test_execution_boundaries.py`: `launch_command` is now `Proceed with 001` (task 192).
- `test_command_budgets_and_noop_delivery_writes_nothing` in `tests/test_command_context.py`:
  delivery now uses 48 Git calls. Raise the limit from 47 to 48.

### 3. CI as a gate

In `.github/workflows/validate.yml`:

- remove `continue-on-error: true` and the comment above it;
- set `cancel-in-progress: ${{ github.ref != 'refs/heads/main' }}`, so that every commit on
  `main` keeps its result;
- add `task-*` to the `push` branches, because `ciBeforeLanding` reads the checks of the
  pushed task branch.

In `.cardine/project.json` (edit by hand: no Cardine command writes this key; a project
change affects new tasks only):

- `"ci": {"provider": "github", "requiredChecks": ["validate"]}`;
- `taskDefaults` gains `"ciBeforeLanding": true`, keeping any existing key;
- `validation.commands` gains `repository-guards`: `python3 scripts/run_tests.py --parallel
  --module test_module_inventory --module test_layout --module test_no_meridian_identifiers
  --module test_text_gates --module test_stop_registry --module test_command_word`;
- `validation.candidate.REUSE`, `BOUNDED` and `FULL` each add `repository-guards`. These
  modules read the records that closure writes, so they can give a new result on the
  candidate even when the code is unchanged (task 201 failed there).
