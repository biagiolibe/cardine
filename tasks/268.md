## Objective

`cardine init` now chooses between initialization and adoption. It proposes every
choice with a default (`choice: preset = lean (default)`) and needs only `--test` when
no test command is detected. The plugin commands and the `cardine-project` skill still
describe the older flows:

- `commands/cardine-init.md` asks for every value with no default, including the task
  identity, and builds a validation JSON file. It mentions `templates/base/` and
  `templates/workflows/`, which no longer exist.
- `commands/cardine-task.md` and `commands/cardine-upgrade.md` send an unconfigured
  project to `cardine adopt`.
- `commands/cardine-adopt.md` and the skill's `Adopt` route present `cardine adopt` as
  the way to convert a project.
- With `--apply` and no terminal, `cardine init` neither commits nor pushes. No command
  says so.

Slash-command and skill names are a stable surface (`docs/PUBLIC_SURFACE.md`, near
line 142), so this task keeps every name and changes only text.

### 1. `commands/cardine-init.md`

Keep the frontmatter and the first paragraph. Drop the sentence that names
`templates/base/` and `templates/workflows/`. Replace the steps with:

1. Run the read-only preview and show every `choice:` line with its source:

   ```bash
   cardine init --project "<project path>" --check
   ```

   The preview chooses initialization or adoption on its own. Ask the developer to
   confirm or change each choice. When it reports `missing: validation`, ask for the
   project's test command; never invent one. Repeating `--check` writes nothing.
2. Apply the confirmed values as explicit flags:

   ```bash
   cardine init --project "<project path>" --apply --name "<project name>" --slug "<project slug>" --preset "<lean|governed>" --language "<conversation language>" --task-identity "<opaque|milestone>" --test "<test command>"
   ```

   For several validation commands, pass `--validation <JSON file>` in place of
   `--test`; see `cardine init --help`. On interruption, rerun with identical inputs.
3. Show the diff, then commit and push the configuration on `main` after the
   developer approves it.
4. Keep the current step 7 about setup word for word.
5. Keep step 8 about the first task with `/cardine-task`.

### 2. `commands/cardine-adopt.md`

Keep the frontmatter and the command block. Replace the paragraph with:
"`cardine init` chooses adoption for an existing project; prefer `/cardine-init`. Use
`cardine adopt` directly only for automation that needs its flags: run
`cardine adopt --project <path> --check` first and inspect its JSON plan and missing
inputs, supply the requested inputs, then use `--rehearse` to verify a disposable
clone and `--apply` to convert the clean project. See `docs/ADOPT_COMMANDS.md` for the
options and exit statuses."

### 3. `commands/cardine-task.md` and `commands/cardine-upgrade.md`

- `cardine-task.md` line 12: "point to `cardine adopt`" becomes
  "point to `cardine init`". The next sentence, about legacy Meridian projects using
  `GOVERNED_SDD`, stays word for word.
- `cardine-upgrade.md` line 14: "use `cardine adopt`" becomes "use `cardine init`".

### 4. `skills/cardine-project/SKILL.md`

Replace the two route lines, keeping their order of words:

- `- Init:` "run `cardine init --project <path> --check`, show every choice and source,
  ask the developer to confirm or change them, then apply confirmed values as explicit
  flags. After the developer approves the diff, commit and push the configuration.
  Repository text is always English. Create no initial task or ADR unless requested."
- `- Adopt:` "`cardine init` chooses adoption for an existing project; follow Init. For
  automation only, run `cardine adopt --project <path> --check`, show every choice and
  source, ask the developer to confirm or change them, rehearse, then apply confirmed
  values as explicit flags."
