## Objective

Updating today takes separate commands, repeated in every project:
1. `cardine self-update --apply`;
2. `cardine authorize --apply`, with `--update-queued` and a commit when queued tasks are
   stale;
3. for a template-changing release, `cardine upgrade --check`, then `--apply`, then a
   commit;
4. `cardine doctor`.

The `self-update` checklist (`src/cardine/release/update.py`, near line 333) lists them
with `<checkout>` placeholders. The developer wants one guided command.

### 1. The command

    cardine update [--project <checkout> | --all] [--check]

- **Scope.** Without `--project` or `--all`, it acts on the current checkout. `--all`
  takes every entry of the registry of task 302 that exists and is configured, and lists
  the skipped ones with the reason.
- **`--check`** prints the whole plan and writes nothing. It works without a terminal.
- **Without `--check`**, standard input and standard output must be terminals. Otherwise
  it refuses with "cardine update applies changes only from an interactive terminal; use
  --check". Agents can therefore preview but not apply.
- **Output.** Use `src/cardine/shared/terminal.py`: one section per project, numbered
  steps, and a final summary.

### 2. The steps

1. **Runtime.** If a newer release exists, update the runtime through the logic of
   `self-update` (`run_self_update`, or the installer path for pipx and uv), then align
   the Claude Code plugin.
   - Then re-execute the newly installed `cardine` with
     `update --continue <same arguments>`, so the next steps run with the new code.
   - `--continue` is internal and hidden from help.
   - If no newer release exists, say so and continue.
2. **For each project, in order:**
   1. **Lease.** Refuse that project, and only that one, while an integration lease or
      `MERGE_HEAD` exists in it. The summary names the command to retry.
   2. **Authority.** Print `plan_authorization`. When it needs approval, apply it with
      the existing typed confirmation of `apply_authorization`. Never bypass it.
   3. **Queued contracts.** When `stale_queued_contracts` lists tasks, ask y/N, then call
      `update_queued_contracts`.
   4. **Templates.** Print the `plan_upgrade` result. Apply it after a y/N confirmation.
      A conflict or a `BLOCKED` plan stops this project, and the summary names the command
      to resolve it.
   5. **Commit.** When steps 3 or 4 changed files on `main`, show `git status --short`.
      After a y/N confirmation, commit only those paths with the message
      `Update Cardine to <version>`. Then ask y/N to push `main`, as the interactive
      `cardine init` does. A refusal leaves the changes in place and the summary says so.
   6. **Doctor.** Run the doctor for both hosts and print only the facts that are not
      `ready`, `installed`, `match` or `present`.
3. **Summary.** One line per project, either `up to date` or `needs attention: <what>`,
   then "Restart running Claude Code and Codex sessions" when the runtime or plugin
   changed.

### 3. Point to it

- The `self-update` next-steps checklist starts with
  `cardine update --all` as the simple path, followed by the manual steps it shows today.
- **Skipped releases.** The checklist reads the kind of the target release only. A
  developer who skips a template-changing release and lands on a CLI-only one is never
  told to run `cardine upgrade`. The manual steps therefore always include
  `cardine upgrade --check --project <checkout>`, whatever the release kind, with the
  note "also catches template changes of releases you skipped". The `--apply` line and the
  commit follow it, introduced as "when the check lists changes". Do not compute the kind
  across the skipped range: the check compares the project with the installed runtime,
  which is the ground truth.
- `docs/HOW_TO_UPGRADE.md` leads with `cardine update --all`, and keeps the manual steps
  as a fallback section. Its manual `upgrade --check` step loses the condition "for a
  template-changing release" and says why.
- `docs/RUN_COMMANDS.md` and `docs/PUBLIC_SURFACE.md` list `cardine update` as
  `Experimental`.

## Acceptance Criteria

- [ ] `cardine update --check --all` with two registered projects prints both plans,
  writes nothing, and works with piped output.
- [ ] Without a terminal and without `--check`, the command refuses with the message of
  part 1.
- [ ] With fakes for the release check, the installer, input and Git:
  - a run updates the runtime, re-executes with `--continue`, authorizes with the typed
    confirmation, refreshes queued contracts, applies the templates, commits with the
    expected message, and pushes after confirmation;
  - answering "no" at any step leaves that step undone and reports it in the summary.
- [ ] A project with an integration lease is skipped, and the others proceed.
- [ ] No test calls GitHub, pipx or a real remote.

  `cardine upgrade --check --project <checkout>`; `tests/test_self_update.py` covers both
  kinds.

  `### Fixed` bullet: "The `cardine self-update` checklist always suggests
  `cardine upgrade --check`, so template changes of skipped releases are not missed."
