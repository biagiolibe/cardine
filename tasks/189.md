# Task 189 — Adopt an existing repository that has no workflow

> **ID**: `189`

## Objective

Let `cardine adopt` install Cardine into an existing repository that has no
workflow yet (case A), so that a real project can start using Cardine.

Today it cannot. Case A plans with `plan_init`, which refuses every path that
`init` would write and already exists. Almost every repository has a
`README.md` or a `.gitignore`, so it fails:

```text
$ cardine init --project . --check ...
error: init conflicts with existing path: README.md; use adoption for an existing workflow
$ cardine adopt --project . --check ...
{"diagnostics": ["init conflicts with existing path: README.md; use adoption for an existing workflow"], "outcome": "blocked", ...}
```

The table of removed surfaces in `docs/ADR_CARDINE_1_0.md` keeps `adopt` for
projects without Cardine (decision 10). The field trial of decision 10 needs a real
project, and the README rewrite (row D1) will send existing projects to `adopt`.
`init` keeps refusing existing paths: it is for a new repository.

## Technical Context

- The adoption rehearsal runs the project's baseline commands on a clone of the
  current commit. A baseline command such as `git diff --check HEAD~1` fails on a
  repository with one commit; that is why the `adopt` variant of the end-to-end test
  declares `git diff --check`.
- During development, run only what the change touches: `python3
  scripts/run_tests.py --parallel --module <name>`, repeating `--module` for several
  modules, and `--last-failed` after a failed full run. Do not run `python3 -m
  unittest` directly, and run the full suite once, as the counted clean-clone
  validation.
- Task 178 edits `scripts/check_repository.py` and its test only; the two tasks share
  no file and can land in either order.
- Other tasks share this machine. Stop only your own processes, by process ID;
  never `pkill` test runs by pattern.

## Developer decisions given in advance

The developer records these decisions in the task contract, so that they
hold however the task is launched, including a bare `Proceed with <TASK-ID>`
from the project console (ADR decision 12). None of these situations needs a
new decision from the developer. After fixing a failure, continue with
revalidation in the same turn; do not stop to report the fix.

- A required command that exits non-zero because of a precondition the agent
  can satisfy (command order, an uncommitted worktree, a missing argument):
  satisfy it and run the command again, once.
- A validation failure caused by this task's own changes, including a name
  collision, a stale reference, a broken link, or a test expectation that the
  task made obsolete: fix it and revalidate, at most 3 counted attempts. A
  test that fails once and passes on an identical unchanged rerun is
  intermittent, recorded in the handoff, and does not count. Only after 3
  counted failures stop and summarize the failures.
- A counted attempt is one run of the whole Validation section on a
  committed implementation that the agent considers complete. Test runs
  during implementation are development, not attempts, however many fail.
  An unfinished implementation is never a reason to stop: finish it first.
- Before the first clean-clone, run `python3 scripts/check_repository.py` and one
  `python3 scripts/run_tests.py --parallel` with one `--module` flag for each edited
  test module and for the repository guards: `test_module_inventory`, `test_layout`,
  the identifier guard (the `tests/test_no_*_identifiers.py` module), `test_text_gates`, `test_stop_registry`, and
  `test_command_word`. Repeat `--module`; a comma-separated list is refused.
- Let a started clean-clone finish; do not interrupt it to restart after a change.
  After a failed clean-clone, fix, commit, and run `python3 scripts/run_tests.py
  --parallel --last-failed` and a `--module` run for each module the fix touched; only
  when both pass, run the clean-clone again as the next counted attempt.
- A stop printed by `cardine run` whose code in `capabilities/stop-codes-v1.json` has
  `human_decision: false`: run the command the stop names, once. If it stops again
  with the same code, stop.
- A test outside the files this record lists that fails only because it expected
  case A of `cardine adopt` to refuse an existing file: update that expectation to
  the behavior below and list the file in the handoff. Any other change outside the
  listed files is a change of scope.
- Before stopping for a change of scope, finish everything else, commit it, and run
  the repository check and the affected tests, so that one stop names every file
  needed. Do not stop once per file.
- A change of scope, a guardrail, and every action the project's workflow denies
  remain stops.
