# Task 288 — Make self-update recognize every published release kind line

> **ID**: `288`

## Objective

On 2026-11-12, `cardine self-update --check` on v0.9.2 printed
`Latest: unknown (release body has no recognized kind line)` and exited 11. No
installation can discover a release through `self-update`.

The two ends disagree:
- `release_kind_from_body` (`src/cardine/release/version.py`, near line 100) accepts a
  first line that starts with `CLI-only release:` or `Template-changing release:`;
- `check_release_notes_contract` (`scripts/prepare_release.py`, near line 50) accepts
  any first line that starts with `CLI-only release` or `Template-changing release`.

The 0.9.0, 0.9.1 and 0.9.2 sections, written by hand as `docs/RELEASING.md` prescribes,
start with `CLI-only release.`. The release workflow publishes them, and the CLI refuses
them.

### 1. The CLI accepts both forms

`release_kind_from_body` recognizes a first non-empty line that starts with the kind
phrase followed by `:` or `.`. Any other text still fails with the same message.

### 2. Releases always publish the form every CLI reads

`check_release_notes_contract` requires the kind phrase followed by `:` as the first
line, for example `Template-changing release: …`. Runtimes up to 0.9.2 read only that
form, so the next release must reach them with it. The error names the expected
prefix.

### 3. `--check` explains an unknown result

When `self-update --check` cannot resolve the latest release, it still prints
`Latest: unknown (<reason>)` and exits 11. It adds two lines:
- what that exit means;
- the manual alternative: the release page URL, and the reinstall or Git command that
  `--to v<version>` would run.

Apply this in `_run_self_update` (`src/cardine/release/update.py`, near line 140) and in
`run_installer_update` (`src/cardine/release/installer.py`, near line 51).

### 4. The release guide

In `docs/RELEASING.md`, step 2, add:
- the `CHANGELOG.md` section starts with `CLI-only release: ` or
  `Template-changing release: `, with the colon;
- a template-changing release is a minor release. A fragment with `### Removed` needs a
  major release, except before `1.0.0`: then a minor release with an `Upgrade notes`
  subsection that names the replacement is enough (amendment of 2026-11-12 in
  `docs/ADR_PUBLIC_SURFACE_AND_STABILITY.md`, decision 2). When a release breaks these
  rules, stop and ask the developer.
