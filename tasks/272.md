# Task 272 — Decide the sources of a review verdict

> **ID**: `272`
> **Category**: Architecture
> **Priority**: 🟠 P2
> **Estimate**: ~3h
> **Assigned to**: unassigned
> **Session**: Consumer report after adoption, 2026-11-11
> **Origin**: friction

Class: SPIKE
Question: From which sources may Cardine accept a review verdict, so that an agent, a teammate in a pull request, or the developer can review, and the record proves who approved? What does each source record, which sources may satisfy `review: required`, and in which order are they built?
Timebox: one session, at most 3 hours of wall time
Deliverable: an ADR at `docs/ADR_REVIEW_VERDICT_SOURCES.md`, and an amendment note in `docs/ADR_CARDINE_1_0.md` decision 14 — not production code

## Context

A consumer on the governed preset found that the only way to record a verdict is the
developer's terminal. Nothing in the templates says so.

The facts, at v0.9.2:
- A verdict without `--owner` requires `--request-id`. That is the identity of a reviewer
  session that Cardine launched and recorded under `run.hostLaunches`
  (`src/cardine/review/verdict.py`, near lines 44 to 60).
- No host adapter launches sessions: "No adapter is installed by default"
  (`src/cardine/hosts/launch.py`). `cardine doctor` reports
  `role-launch-reviewer: unsupported (D3)` on both hosts.
- So every governed verdict is an owner verdict. `cardine run` already prints
  `cardine review verdict <ID> APPROVE --owner …` (`src/cardine/lifecycle/engine.py`, near
  line 174).
- The templates still describe the reviewer session recording its verdict with
  `--request-id`:
  - `templates/single/PROJECT_WORKFLOW.md`, block `review-policy v2`;
  - `templates/single/docs/workflows/REVIEW.md`, block
    `task-worktree-review-procedure v4`.
- The review projection already records `approved_by` (`owner` or `reviewer`) and
  `source='local'` (`verdict.py`, near line 141).
- The project declaration accepts `landingMode: "direct"` only ("only direct is supported
  in 1.0", `src/cardine/shared/project.py`, near line 50). It knows a CI provider,
  `github`, whose required checks the engine already polls before landing.
- `docs/ADR_CARDINE_1_0.md` decision 14, rule 2, says: "The engine launches the
  implementer and the reviewer with distinct host profiles". Its "Developer channel"
  amendment of 2026-11-03 makes the developer record verdicts while hosts cannot prove
  their role profiles.

## Developer decisions (2026-11-11)

- Review must be possible beyond the owner, and the direction must lead toward pull
  requests and teams with manual review.
- Rejected:
  - an unverified reviewer verdict that any session may record: it removes the
    guarantee that nobody approves their own work;
  - refusing a verdict from the implementer's host session id: it is a local
    heuristic that does not reach a teammate on a forge.
- The model to decide is "a verdict comes from a source that proves the approver's
  identity". There are three candidates:
  - **owner**: the developer at an interactive terminal; it exists today;
  - **forge**: a pull request approval by an account other than the author, read from
    GitHub;
  - **launched reviewer**: an agent session that Cardine starts in a fresh process,
    with no edit tools, whose verdict Cardine records itself.
- The coordinator recommends building the forge source first and the launched reviewer
  second. The ADR confirms or changes this, with reasons.

## What the ADR must settle

1. For each source:
   - what proves identity;
   - what Cardine records: `approved_by`, `source`, the reviewed commit, and for the
     forge the PR number, the review id and the approver's login;
   - which declared limit applies, as decision 14 states one for same-user receipts.
2. Which sources satisfy `review: required`, and whether a project can restrict them, for
   example by allowing only `forge`. Name the declaration key, if any. The schema
   change itself is out of scope.
3. The forge source:
   - how it relates to `landingMode: "pull-request"`. Does reading an approval need PR
     landing, or can a direct landing read the approval of a PR opened for the task
     branch?
   - what happens when the PR head moves after approval;
   - how a dismissed review is handled.

   State which GitHub facts the ADR relies on, and mark each as documented (with the
   source) or still to verify by probe. For example, that the author cannot approve
   their own PR, and that a review carries the reviewed `commit_id`.
4. The launched reviewer:
   - what each host must enforce (no edits, no `cardine review verdict` by the child);
   - how Cardine starts the child and collects its verdict;
   - what `cardine doctor` must prove before reporting it supported;
   - which host flags it relies on, each marked documented or still to verify. Run
     no paid agent call in this spike.
5. Mixed review:
   - an agent reviewer posts its findings in the PR, and a person approves;
   - two consecutive `CHANGES_REQUESTED` still end in `REVIEW_LOOP_EXHAUSTED`, whatever
     the source.
6. The order of work items after the ADR. Each one is small enough for a task of about
   10 files. Include the template correction for the review blocks and the owner
   procedure, which can ship before any new source.
