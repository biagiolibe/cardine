## Objective

In a Cardine project the console cannot launch any task. Run on a ready task answers:

```text
Host role boundary unavailable: configure the selected enforced host profiles
```

`_launch_selected` in `src/cardine/console/launch.py` sends every product task to the
engine's role launch, which needs `host_adapter()`. That function in
`src/cardine/lifecycle/control.py` returns `None` by design: decision D3 of
`docs/HOST_CAPABILITY_CONTRACT.md` makes engine role launches `unsupported` on both
hosts until a host can prove its policy. No configuration changes that, so the message
asks for something the developer cannot do. Before the switch, tasks were legacy and
the console started an agent session instead.

The console also shows the wrong directive for these tasks. "Next directive" and
`[copy]` give the engine command `cardine run <ID> --project <primary>`, which an agent
runs, instead of `Proceed with <ID>`, which the developer gives the agent. Typing the
engine command by hand advances the engine one step, but nobody implements the task.

When no enforced host channel exists, let Run start the developer's own agent session
in a new iTerm2 pane with the assignment `Proceed with <ID>`, through the same
`_launch_request` and `_start_launch` path that legacy tasks use. That is exactly what
the developer does by hand today: the session follows `cardine-delivery`, which calls
`cardine run` and performs the step it returns. It is not an engine role launch, so D3
is unchanged. Cancel and Abort still require an enforced adapter, and an enforced
adapter, once one exists, still takes precedence.

For product tasks, show `Proceed with <ID>` as the directive, the next action, and the
`[copy]` text whenever the engine has a next step, `Review <ID>` when the step
launches a reviewer, and `Address review <ID>` when the review requested changes. Run
uses the same directive.

## Technical Context

- `Task.launch_command` drives the directive, `[copy]`, the launch panel, and Run, so one
  change in `src/cardine/console/models.py` covers them all.
- Scope widened by the developer on 2026-11-08, before the task started.
- The engine role launch and its adapter are `src/cardine/hosts/launch.py` and
  `src/cardine/lifecycle/engine.py`; neither changes.
- `cardine console` is Experimental (decision 7 of `docs/ADR_CARDINE_1_0.md`).
- During development, run only what the change touches: `python3
  scripts/run_tests.py --parallel --module <name>`, repeating `--module`. Do not run
  `python3 -m unittest` directly. Run the full suite once, as the counted
  clean-clone validation.
- Run validation suites one at a time and redirect each one's output to a log file
  with its exit code appended, so the result survives a lost process handle.
- Other tasks share this machine. Stop only your own processes, by process ID;
  never `pkill` test runs by pattern.

## Developer decisions given in advance

The developer records these decisions in the task contract, so that they
hold however the task is launched, including a bare `Proceed with <TASK-ID>`
from the project console (ADR decision 12). None of these situations needs a
new decision from the developer. After fixing a failure, continue with
revalidation in the same turn; do not stop to report the fix.

- A required command that exits non-zero because of a precondition the agent
  can satisfy (command order, an uncommitted worktree, a missing argument):
  satisfy it and run the command again, once.
- A validation failure caused by this task's own changes: fix it and revalidate, at
  most 3 counted attempts. A test that fails once and passes on an identical
  unchanged rerun is intermittent, recorded in the handoff, and does not count.
  Only after 3 counted failures stop and summarize the failures.
- A counted attempt is one run of the whole Validation section on a committed
  implementation that the agent considers complete. Test runs during
  implementation are development, not attempts.
- Before the first clean-clone, run `python3 scripts/check_repository.py` and one
  `python3 scripts/run_tests.py --parallel` with one `--module` flag for each edited
  test module and for the repository guards: `test_module_inventory`, `test_layout`,
  the identifier guard (the `tests/test_no_*_identifiers.py` module),
  `test_text_gates`, `test_stop_registry`, and `test_command_word`. Repeat
  `--module`; a comma-separated list is refused.
- Let a started clean-clone finish; do not interrupt it. After a failed clean-clone,
  fix, commit, and run `python3 scripts/run_tests.py --parallel --last-failed` and a
  `--module` run for each module the fix touched before the next counted attempt.
- A stop printed by `cardine run` whose code in `capabilities/stop-codes-v1.json` has
  `human_decision: false`: run the command the stop names, once. If it stops again
  with the same code, stop.
- A console test outside the listed files that fails only because it expected Run to
  refuse without an enforced host: update that expectation and list the file in the
  handoff. Any other change outside the listed files is a change of scope.
- Before stopping for a change of scope, finish everything else, commit it, and run
  the repository check and the affected tests, so that one stop names every file
  needed.
- A change of scope, a guardrail, and every action the project's workflow denies
  remain stops.
