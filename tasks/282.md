# Task 282 — Let cardine run launch the reviewer and record its verdict

> **ID**: `282`
> **Category**: Feature
> **Priority**: 🔴 P1
> **Estimate**: ~3h
> **Assigned to**: unassigned
> **Session**: Launched reviewer, 2026-11-12
> **Origin**: plan

## Objective

After tasks 279 to 281:
- Cardine can record a launched reviewer's verdict from its answer;
- Codex and Claude reviewers can be launched without write capability;
- `cardine doctor` can prove that.

Nothing launches the reviewer yet. This task makes the review step of `cardine run`
launch it, wait for it, and record its verdict, so a project can require review without
the developer's terminal on every task.

### 1. The declaration

In `src/cardine/shared/project.py`, add `launched` to the available review sources
(the constant that task 275 introduced). Add the optional key `review.reviewer`, with the
value `codex` or `claude`, to `.cardine/project.json` and
`schemas/project-v1.schema.json`. The parser rejects:
- `review.sources` containing `launched` without `review.reviewer`;
- `review.reviewer` without `launched` in `review.sources`.

`review.reviewer` is read from the declaration on `main` at launch time. It is not
frozen into the contract: it names the host that runs the reviewer, not a policy. A
change takes effect at the next launch. `reviewSources` stays frozen, as task 275 built
it.

### 2. The review step

In `run_worktree_step` (`src/cardine/lifecycle/engine.py`), when review is required, CI
has passed (task 278), the review is not approved, and the frozen `reviewSources`
contain `launched`:

1. Build the adapter:
   - the transport for `review.reviewer`, with the request directory under the Git
     common directory at `cardine-hosts/<host>`;
   - the reviewer policy of tasks 280 and 281;
   - the doctor proof from `role_launch_states`.

   If the reviewer profile is not `ready`, stop with `COMMAND_REFUSED` and the detail
   "launched reviewer unavailable: role-launch-reviewer is <state>; run cardine doctor,
   or record the verdict with --owner when reviewSources allow owner".
2. Call `launch_work` for the reviewer with the current head. It is idempotent per
   attempt, so a rerun polls the same session and never starts a second one.
3. While the response is missing, return `waiting` with `retry_after_seconds` 30 and the
   same `cardine run` command.
4. When the response exists, call `record_launched_verdict` (task 279), then continue as
   after an owner verdict. `CHANGES_REQUESTED` returns `iterate` with the findings.
   `BLOCKED` stops as an owner `BLOCKED` does.

When `reviewSources` contain both `owner` and `launched`, the launch happens, and an
owner verdict recorded first still counts. When they do not contain `launched`, the
step is unchanged.

### 3. Documentation

- `docs/PROJECT_DECLARATION.md`, section "Review sources" (task 275): document
  `launched` and `review.reviewer`, with a short example, and say that the reviewer has
  no write capability and that `cardine doctor` must report `role-launch-reviewer:
  ready`.
- `docs/RUN_COMMANDS.md`: one sentence in the review paragraph. With `launched`,
  `cardine run` launches the reviewer, returns `waiting` while it works, and records its
  verdict.

  review task with `reviewSources: ["launched"]`:
  - launches once;

  - continues to the candidate.
