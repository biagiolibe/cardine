## Objective

With `ciBeforeLanding` and required review, `cardine run` asks for the review before it
runs CI (`resolve_run` in `src/cardine/lifecycle/engine.py`, near lines 172 to 183). A
reviewer approves without the full suite, which runs only on CI. When CI then fails,
the task goes back to implementation and needs another review round. Projects that keep
local validation short and leave the full suite to CI pay one review round for every CI
failure.

This task moves the CI gate before the review step. The run order becomes:
- delivery, then local task validation;
- refresh from main when due, then CI on the delivered head;
- review;
- candidate, then landing.

### 1. Gate order

In `resolve_run` and `run_worktree_step`, when the contract has a CI policy
(`ci.ci_policy(state['contract'])`), run `run_ci_step` after local validation passes
and before the review step is returned. The review step, with its owner command, is
returned only after CI has passed for the current task head. A task without a CI policy
behaves exactly as today.

A CI failure returns `iterate` to implementation, as today, and consumes no review
attempt and no `CHANGES_REQUESTED` budget.

### 2. CI binding

In `ci_binding` (`src/cardine/integration/ci.py`, near line 116), drop `attempt` from the
binding. A cached pass is bound to repository, ref, head, contract and checks. After
`CHANGES_REQUESTED`, the next delivery has a new head and therefore a new CI run. Keep
the one plain push per delivered head and its `ci-push` receipt.

### 3. APPROVE requires the pass

In `src/cardine/review/verdict.py`, when the contract has a CI policy, refuse an `APPROVE`
whose reviewed HEAD has no receipt-covered `run.ci` pass. Use `REVIEW_NOT_APPROVED` and
the detail "cause: missing; required checks have not passed for <head>; run cardine run
<ID> first". Reuse the cause `missing`, so that the stop registry entry does not change. `CHANGES_REQUESTED` and `BLOCKED` stay possible without a pass.

### 4. Main moves after approval

Main may advance while a review is in progress. Define this behavior and test it:

- Before review, a due refresh merges main as today, then CI runs on the merged head.
- After approval, when a refresh is due, Cardine merges main with `merge_main`. If the
  merge is clean, the approval stays valid. CI runs again on the merged head before the
  candidate. The approval does **not** become stale because of the paths that main
  brought in.
- If the refresh merge conflicts, the existing `INTEGRATION_CONFLICT` stop applies. The
  resolution is a new commit by a person or agent, so it needs a new delivery and a new
  review.

First write a test that shows what happens today when a clean refresh lands after an
approval. Look at the landing check in `src/cardine/integration/merge.py` near lines 120
to 140: the paths between `reviewed_commit` and the task commit include main's commits.
If the test shows that the approval is refused as stale, fix the check. Exclude the
commits reachable from the merged main commit that `record_base` records, and keep
refusing any other path. Keep the test in either case.

### 5. Documentation

- `docs/RUN_COMMANDS.md`, in the paragraph on required CI near line 56: one sentence
  saying that with required review, CI runs on the delivered head before the review
  step, and that `APPROVE` needs the pass.
- `docs/RULE_ENFORCEMENT_INVENTORY.md`, row PW-35: change "once per review attempt" to
  "once per delivered head", and add "Task 278: CI runs before review."

## Technical Context

- **Developer decisions** (2026-11-12):
  - CI must be green before a review is approved.
  - A clean merge of main after approval needs CI again, not a new review.
- The order is sequential: the review waits for CI. Running review and CI in parallel
  is a later choice for the forge source, where the pull request shows both.
- `require_ci_pass` in `ci.py` is the read-only check that staging already uses. Reuse
  it in part 3 if its binding fits after part 2.
- Sweep before finishing: `git grep -n "attempt" -- src/cardine/integration/ci.py tests/test_run_ci.py`
  and `git grep -n "ci_pending\|review_approved" -- src/cardine/lifecycle`.
- The review templates do not describe the CI order. Do not edit them; the review role
  start budget is nearly full.
- During development, run tests with
  `python3 scripts/run_tests.py --parallel --module <name>`.
