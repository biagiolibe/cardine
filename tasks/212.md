## Objective

Codex hooks are registered twice in a project that Cardine manages: by the user registry
`~/.codex/hooks.json`, which `cardine setup` writes, and by the project copy
`.codex/hooks.json`, which the template distributes. `read-guard` and `stop-audit` are in
both. The project copy also has a second defect: it runs the bare command `cardine hook
...`, so a Codex process whose `PATH` lacks `cardine` fails with exit 127. Task 200 made
the command absolute only in the user registry; a tracked project file cannot hold a
machine-specific path.

`docs/HOST_INTEGRATION_PLAN.md` already chose the user registry ("no new consumer hook
copies"). This task stops distributing the project copy.

Remove:

- `templates/single/.codex/hooks.json` and this repository's `.codex/hooks.json`;
- this repository's entry for it: the `managedFiles` key in `.cardine/manifest.json` and
  the file `.cardine/baselines/1.4.0/.codex/hooks.json`. Edit these two by hand: no
  Cardine command removes a managed surface, and the repository check passes after it;
- the `managed-copy` surface with path `.codex/hooks.json` in
  `capabilities/catalog-v1.json`;
- the line naming it in `scripts/check_repository.py`, in the optional paths of
  `src/cardine/templates/files.py`, and in `commands/cardine-init.md`.

`src/cardine/hosts/hooks.py` does not change: `_foreign_advisories` still reports a
project copy left in an existing consumer as a possible double registration. Do not
delete a consumer's copy.

Update `docs/AGENT_OPERATIONS.md` ("Codex hooks and command approvals" and "Codex large-file
read guard in Governed SDD"): the hooks are registered in `~/.codex/hooks.json` by `cardine
setup --apply`, and reviewed once in `/hooks`. Add a `Removed` line to `CHANGELOG.md`.
