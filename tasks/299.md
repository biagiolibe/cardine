# Task 299 — Tell everyday users when a new Cardine release is available

> **ID**: `299`
> **Category**: Feature

> **Estimate**: ~3h

> **Origin**: plan

## Objective

A developer learns about a new release only by running `cardine self-check` or
`cardine self-update --check`. The developer wants daily users to be told when a release
is available. The notice must cost nothing on a normal turn, work offline, and be easy
to turn off.

### 1. A cached release check

Add `src/cardine/release/notice.py`.

- `~/.cardine/update-check.json` caches the last check:
  `{"checkedAt": <UTC ISO>, "installed": "<version>", "latest": "<version>" | null, "kind": "CLI-only" | "template-changing" | null}`.
  Write it atomically, owner-only.
- `refresh(home, installed)` calls `fetch_latest_release` (`src/cardine/release/update.py`)
  with a timeout of 2 seconds and writes the cache. A failure writes `latest: null` with
  the time of the attempt, so the next attempt waits for the next window.
- `notice(home, installed)` reads the cache only and never touches the network. It
  returns the notice text when the cached `latest` is newer than `installed`, otherwise
  `None`. The text is:

      Cardine <latest> is available (installed <installed>, <kind> release): cardine self-update --check

- `refresh_in_background(home, installed)` does nothing when the cache is less than 24
  hours old. Otherwise it starts `refresh` in a detached process, with no inherited
  terminal, and returns immediately.
- **Opt-out:**
  - no check and no notice when `CARDINE_NO_UPDATE_NOTICE` is set to any non-empty
    value, or when `CI` is set;
  - the only network call is the existing GitHub API request, whose user agent carries
    only the Cardine version.

### 2. Where the notice appears

- **Per-turn briefing** (`src/cardine/hosts/briefing.py`). When `notice` returns text,
  the briefing adds the line
  `Cardine update: <notice text>; tell the developer once in this session.`
  It then calls `refresh_in_background`. The briefing never waits for the network.
- **Interactive commands.** After `cardine guide`, `cardine status` and `cardine doctor`
  finish, when standard error is a terminal, print the notice on standard error as one
  `note` line (`src/cardine/shared/terminal.py`), then call `refresh_in_background`.
  `cardine run`, `--format json` output and every non-terminal invocation print nothing
  and start nothing.
- **Console.** The header shows `↑ <latest> available` when `notice` returns text. On
  start, the console calls `refresh_in_background`.

### 3. Documentation

In `docs/HOW_TO_UPGRADE.md`, add a short section "Update notices" that says:
- where the notice appears;
- how often Cardine checks;
- which single request it makes;
- that `CARDINE_NO_UPDATE_NOTICE=1` turns it off.

## Technical Context

- **Developer decision** (2026-11-12): daily users are told when a release is available,
  without slowing a turn or a command.
- The per-turn briefing runs on every prompt, so it must read the cache only.
- The detached refresh must not leave a zombie or write outside `~/.cardine`. Use
  `start_new_session=True` and no inherited standard streams, as
  `src/cardine/hosts/transports.py` starts its wrapper.
- During development, run tests with
  `python3 scripts/run_tests.py --parallel --module <name>`.

## Out of scope

- Updating automatically.
- Notices inside `cardine run` JSON.
- Release channels other than the latest GitHub release.
